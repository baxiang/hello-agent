## 一、项目定位与核心理念

Hermes Agent 不是又一个"ChatGPT 包装器"。它是 Nous Research 构建的**自我改进型 AI Agent 平台**——唯一内置学习闭环的 Agent：从经验中创建技能、使用中改进技能、跨会话持久化知识、搜索历史对话、构建用户模型。

三个核心设计哲学贯穿整个代码库：

1. **注册 ≠ 暴露**：工具注册到全局 Registry 后，必须显式分配到 Toolset 才会暴露给模型，防止能力泄露
2. **插件不得修改核心**：需要新能力时扩展插件表面（新 Hook、新 ctx 方法），而非硬编码插件逻辑
3. **缓存完整性**：对话中途不修改工具集/系统提示，避免破坏 Prompt Cache 导致成本飙升

### 2.2 进程模型

Hermes 有三种运行模式，每种有不同的进程拓扑：

**CLI 模式**：单进程，prompt_toolkit 驱动交互
```
用户终端 → cli.py (prompt_toolkit) → AIAgent → OpenAI API
                                     ↕
                              tools/*.py (本地执行)
```

**TUI 模式**：双进程，Ink/React 前端 + Python 后端
```
用户终端 → Node.js (Ink/React)
              ↕ stdio JSON-RPC
           Python (tui_gateway/) → AIAgent → OpenAI API
```

**Gateway 模式**：单进程多线程，服务多个消息平台
```
Telegram ─┐
Discord  ─┤
Slack    ─┼→ gateway/run.py → AIAgent (每会话一个)
WhatsApp ─┤                   ↕
Signal   ─┘            tools/*.py + cron/scheduler.py
```

### 2.3 依赖链

核心模块的导入顺序严格受控，防止循环依赖：

```
tools/registry.py  (零依赖，被所有工具文件导入)
       ↑
tools/*.py  (每个在模块级调用 registry.register())
       ↑
model_tools.py  (导入 tools/registry + 触发工具发现)
       ↑
run_agent.py, cli.py, batch_runner.py, environments/
```

## 三、Agent 循环深度剖析

### 3.1 核心循环

`agent/conversation_loop.py` 实现了完整的对话循环。这是整个系统最关键、最复杂的部分：

```python
# 简化版核心循环
while (api_call_count < self.max_iterations and self.iteration_budget.remaining > 0) \
        or self._budget_grace_call:
    
    # 1. 中断检查
    if self._interrupt_requested: break
    
    # 2. 调用 LLM
    response = client.chat.completions.create(
        model=model, messages=messages, tools=tool_schemas
    )
    
    # 3. 分支：工具调用 vs 最终响应
    if response.tool_calls:
        for tool_call in response.tool_calls:
            result = handle_function_call(tool_call.name, tool_call.args, task_id)
            messages.append(tool_result_message(result))
        api_call_count += 1
        
        # 上下文压缩检查
        if compression_enabled and should_compress(real_tokens):
            messages = compress_context(messages, system_message)
        
        continue  # 继续循环
    else:
        return response.content
```

### 3.2 异常恢复矩阵

实际代码远比简化版复杂。Hermes 处理了多达 **8 种异常情况**：

| 异常场景 | 检测方式 | 恢复策略 | 最大重试 |
|---------|---------|---------|---------|
| **空响应** (无内容无推理) | `_has_content_after_think_block()` 返回 False | 重试同一 API 调用 | 3 次 |
| **仅推理无内容** (思考模型) | `reasoning` 字段有值但 `content` 为空 | 追加 assistant 消息 + 继续 (prefill) | 2 次 |
| **无效 JSON 参数** | `json.loads()` 失败 | 重试 API 调用；3 次后注入恢复工具结果 | 3 次 |
| **截断响应** | `finish_reason="length"` + 参数不以 `}` 或 `]` 结尾 | 返回 partial 结果 | 1 次 |
| **工具调用后空响应** | 工具结果后模型返回空 | 注入 nudge 用户消息 | 1 次 |
| **housekeeping 工具后空响应** | 上一轮内容 + memory/todo 工具调用 | 使用上一轮内容作为最终响应 | 0 次 |
| **部分流恢复** | 流中断但已有内容到达 | 使用已流式传输的内容 | 0 次 |
| **所有重试耗尽** | 重试计数器达到上限 | 尝试回退提供商链 | 链长度 |

这种多层恢复机制确保了 Agent 在面对各种模型异常时的鲁棒性。

### 3.3 迭代预算系统

```python
class IterationBudget:
    max_total: int        # 最大迭代次数 (默认 90)
    used: int             # 已用迭代
    remaining: int        # 剩余迭代
    
    def refund(self):     # 退还一次迭代 (execute_code 不消耗预算)
```

**预算退费机制**：当唯一的工具调用是 `execute_code`（程序化工具调用 RPC）时，自动退费，因为这些调用是零上下文成本的管道操作。

**Grace Call**：预算耗尽后的最后一次调用机会，让模型有机会生成摘要。

### 3.4 Turn Exit 诊断

每次对话结束时记录详细的退出原因：

```python
result = {
    "final_response": final_response,
    "turn_exit_reason": _turn_exit_reason,
    "api_calls": api_call_count,
    "input_tokens": agent.session_input_tokens,
    "output_tokens": agent.session_output_tokens,
    "cache_read_tokens": agent.session_cache_read_tokens,
    "estimated_cost_usd": agent.session_estimated_cost_usd,
    "model": agent.model,
    "provider": agent.provider,
    # ...
}
```

## 四、工具系统深度剖析

### 4.1 工具注册中心 (Registry)

`tools/registry.py` 是零依赖单例，整个工具系统的基础：

```python
class ToolRegistry:
    def register(self, name, toolset, schema, handler, 
                 check_fn=None, requires_env=None, 
                 is_async=False, override=False):
        """注册工具——由每个工具文件在模块导入时调用"""
```

**关键设计决策**：

1. **AST 扫描发现**：用 `ast.parse()` 扫描 `tools/` 目录，只导入包含顶层 `registry.register()` 调用的模块：

```python
def _module_registers_tools(module_path: Path) -> bool:
    source = module_path.read_text(encoding="utf-8")
    tree = ast.parse(source, filename=str(module_path))
    return any(_is_registry_register_call(stmt) for stmt in tree.body)
```

2. **check_fn TTL 缓存**：工具可用性检查结果缓存 30 秒

3. **线程安全快照**：读写分离，读操作通过 `_snapshot_state()` 获取一致性快照，写操作通过 `threading.RLock` 串行化

4. **代际计数器**：每次注册/注销操作递增 `_generation`，外部调用方可据此做缓存失效判断

5. **影子覆盖保护**：不同 toolset 的同名工具默认不允许互相覆盖，必须显式 `override=True`

6. **动态 Schema 覆盖**：`dynamic_schema_overrides` 允许工具在每次 `get_definitions()` 时动态修改 schema

### 4.2 工具集系统 (Toolsets)

`_HERMES_CORE_TOOLS` 定义了所有平台共享的约 50 个基础工具。每个平台在核心基础上添加特有工具。

工具集支持递归组合，带循环检测：

```python
"debugging": {
    "tools": ["terminal", "process"],
    "includes": ["web", "file"]  # 递归解析
}
```

特殊别名 `"all"` 或 `"*"` 解析为所有工具集的并集。

### 4.3 工具护栏 (Guardrails)

`agent/tool_guardrails.py` 实现了纯函数式的工具调用循环检测：

```python
@dataclass(frozen=True)
class ToolCallGuardrailConfig:
    warnings_enabled: bool = True          # 警告默认开启
    hard_stop_enabled: bool = False        # 硬停止默认关闭
    exact_failure_warn_after: int = 2      # 相同工具+相同参数失败 2 次后警告
    same_tool_failure_halt_after: int = 8  # 同工具失败 8 次后硬停止
    no_progress_warn_after: int = 2        # 幂等工具无进展 2 次后警告
```

工具分两类：**幂等工具**（只读如 `read_file`, `web_search`）和**变异工具**（有副作用如 `terminal`, `write_file`）。检测基于 `ToolCallSignature`（工具名 + SHA-256 参数哈希），不暴露原始参数值。

## 五、技能系统深度剖析

技能是 Hermes 最独特的特性——**程序性记忆**。它让 Agent 从经验中学习并改进。

### 5.1 技能索引与三层缓存

`build_skills_system_prompt()` 使用三层缓存加速技能索引构建：

```
Layer 1: 进程内 LRU 缓存 (_SKILLS_PROMPT_CACHE, 最多 8 条)
    ↓ miss
Layer 2: 磁盘快照 (.skills_prompt_snapshot.json, mtime/size manifest 验证)
    ↓ miss
Layer 3: 完整文件系统扫描 (冷路径，扫描后写入快照)
```

快照通过比较 SKILL.md/DESCRIPTION.md 的 `mtime_ns + st_size` 判断是否过期。

**条件激活**：技能可声明 `fallback_for_toolsets`（主工具可用时隐藏）和 `requires_tools`（必要工具不可用时隐藏）。

### 5.2 Curator（技能生命周期管理）

`agent/curator.py` 后台自动维护系统，状态机: active -> stale -> archived（30天/90天未使用）。

**严格不变量**：只触碰 `created_by: "agent"` 的技能；永不删除，最多归档（可恢复）；Pinned 技能豁免所有自动转换。

## 六、记忆系统深度剖析

### 6.1 记忆提供者 ABC

`agent/memory_provider.py` 定义了 `MemoryProvider` 抽象基类：

```python
class MemoryProvider(ABC):
    # 核心生命周期
    def is_available(self) -> bool          # 配置/凭据检查
    def initialize(self, session_id, **kw)  # 连接/创建资源
    def system_prompt_block(self) -> str    # 注入系统提示的静态文本
    def prefetch(self, query) -> str        # 每轮前的背景召回
    def sync_turn(self, user, asst)         # 每轮后的异步写入
    def get_tool_schemas(self) -> List[Dict]# 暴露给模型的工具 schema
    def handle_tool_call(self, name, args)  # 分发工具调用
    def shutdown(self)                      # 清理
    
    # 可选钩子
    def on_turn_start(turn, message, **kw)
    def on_session_end(messages)
    def on_session_switch(new_id, **kw)
    def on_pre_compress(messages) -> str
    def on_memory_write(action, target, content)
    def on_delegation(task, result, **kw)
```

### 6.2 记忆管理器

`agent/memory_manager.py` 强制**单一外部提供者**限制，防止工具 schema 膨胀和冲突。

**上下文围栏**：使用 `<memory-context>` XML 标签包裹预取的记忆上下文，防止模型混淆记忆和新输入。`StreamingContextScrubber` 是一个状态机，在流式输出中实时剥离这些标签，防止泄露到用户界面。

### 6.3 内置记忆 + 外部后端

- **内置**：`MEMORY.md`（个人笔记）+ `USER.md`（用户档案），纯文件存储
- **外部**：honcho（方言式用户建模）、mem0、supermemory、byterover、hindsight 等
- 所有外部后端**镜像**内置记忆写入（通过 `on_memory_write` 钩子）

## 七、子代理委派深度剖析

### 7.1 架构

`tools/delegate_tool.py` 实现了子代理委派系统：

```python
DELEGATE_BLOCKED_TOOLS = frozenset([
    "delegate_task",   # 禁止递归委派
    "clarify",         # 禁止用户交互
    "memory",          # 禁止写入共享记忆
    "send_message",    # 禁止跨平台副作用
    "execute_code",    # 子代理应逐步推理
])
```

### 7.2 两种形态

**单任务**：`delegate_task(goal="...", context="...", toolsets=[...])`

**批量并行**：`delegate_task(tasks=[{goal, context}, ...])`，每个任务独立子代理并发执行，并发上限 `delegation.max_concurrent_children`（默认 3）。

### 7.3 角色体系

- `role="leaf"`（默认）：聚焦工作器，不能调用 delegate_task/clarify/memory 等
- `role="orchestrator"`：保留 delegate_task，可继续生成子代理，受 max_spawn_depth（默认 2）限制

### 7.4 子代理审批回调

子代理运行在 ThreadPoolExecutor 工作线程中，不继承父级的交互式审批回调。默认自动拒绝危险命令，防止 input() 死锁。

## 八、系统提示词工程

### 8.1 提示词组装顺序

`agent/system_prompt.py` 按固定顺序组装：

1. SOUL.md (Agent 身份/人格)
2. 环境提示 (OS, 主目录, 工作目录, WSL 等)
3. 平台提示 (Telegram/Discord/CLI 格式规范)
4. 上下文文件 (.hermes.md > AGENTS.md > CLAUDE.md > .cursorrules)
5. 技能索引 (<available_skills>)
6. 记忆上下文 (<memory-context>)
7. Nous 订阅状态
8. 计算机使用提示 (macOS 背景桌面控制)

### 8.2 平台适配提示

每个消息平台有定制的格式提示：WhatsApp/Signal 不使用 Markdown；Telegram 自动转换 Markdown 但无表格；CLI 用简单文本；Cron 无用户在场完全自主；SMS 纯文本限 1600 字符。

### 8.3 Anthropic Prompt 缓存策略

`system_and_3` 策略：在系统提示 + 最后 3 条非系统消息上放置 cache_control 断点，多轮对话中减少约 75% 的输入 token 成本。

## 九、Cron 定时任务系统

- `tick()` 由 Gateway 每 60 秒调用，文件锁防止多进程重复执行
- 三个受保护工具集始终禁用：`cronjob`, `messaging`, `clarify`
- Cron 会话默认跳过记忆（skip_memory=True）
- 3 分钟硬中断防止失控 Agent 循环

## 十二、依赖安全策略

经历了 litellm 妥协和 Mini Shai-Hulud 蠕虫后建立严格策略：核心依赖 `==exact` 精确锁定；非核心 `>=floor,<next_major`；Git URL 用提交 SHA；GitHub Actions 用提交 SHA + 注释。

## 十三、测试体系

- 子进程隔离：每个测试运行在独立 Python 子进程中，消除状态泄漏
- 反变更检测测试：禁止快照测试，应该写不变量测试
- 测试包装器确保 CI 环境：unset API keys、临时 HOME、UTC 时区、C.UTF-8

---

## 十四、安全系统

- 危险命令审批：终端工具对危险命令要求用户确认
- 文件安全：agent/file_safety.py 阻止写入敏感路径
- URL 安全：tools/url_safety.py 阻止访问内部网络（SSRF 防护）
- 威胁模式：tools/threat_patterns.py 检测注入模式
- 工具输出限制：防止上下文窗口被淹没
- 错误净化：清理工具错误消息中的框架标记/CDATA/围栏

## 十五、文件变异验证

Agent 完成一轮后验证所有 write_file / patch 调用是否真的成功。失败且未被覆盖的自动附加验证脚注，解决模型"过度声称"问题。

## 十六、总结：关键设计模式

| 模式 | 实现 | 解决的问题 |
|------|------|-----------|
| 注册不等于暴露 | Registry + Toolsets 分离 | 防止能力泄露给模型 |
| 插件不得修改核心 | 扩展插件表面而非硬编码 | 保持核心简洁 |
| 缓存完整性 | 对话中不修改工具集/系统提示 | 避免 Prompt Cache 失效 |
| 子进程测试隔离 | multiprocessing spawn | 消除状态泄漏 |
| 技能永不删除 | Curator 只归档 | 数据安全 |
| 委派深度限制 | max_spawn_depth=2 | 防止无限递归 |
| 凭据池 | 多 API Key 轮换 | 避免单一 Key 限流 |
| 辅助客户端 | 每任务独立模型配置 | 灵活资源分配 |
| 上下文围栏 | memory-context XML 标签 | 防止记忆混淆新输入 |
| 流式上下文清洗 | StreamingContextScrubber | 防止标签泄露到 UI |
| 影子覆盖保护 | override=True 显式选择 | 防止意外覆盖 |
| 精确依赖锁定 | ==X.Y.Z 核心依赖 | 供应链攻击防护 |
| 文件变异验证 | 失败脚注附加 | 防止过度声称 |
| 代际计数器 | _generation 递增 | 缓存失效判断 |
| AST 扫描发现 | ast.parse() 自动导入 | 零维护导入列表 |
