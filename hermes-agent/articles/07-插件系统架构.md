# Hermes Agent 插件系统架构

> **项目**: [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) | **版本**: v0.15.1
> **核心文件**: `hermes_cli/plugins.py` (~2000 行) · `agent/memory_provider.py` (~290 行) · `providers/__init__.py` (~180 行)

---

## 一、设计哲学：核心瘦身，插件承载

Hermes Agent 的插件系统遵循一个铁律：**核心代码不知道任何插件的具体实现**。核心框架只提供抽象基类和调度循环，具体能力——记忆后端、模型提供商、上下文引擎、图像生成、看板、会议集成——全部以插件形式存在。当需要新能力时，不是往核心塞代码，而是扩展通用插件表面（新 hook 或新 `ctx` 方法），让插件通过标准接口接入。

PR [#5295](https://github.com/NousResearch/hermes-agent/pull/5295) 是这一哲学的里程碑：它从核心代码中移除了 **95 行硬编码的 honcho 代码**。在此之前，honcho 的内存写入逻辑直接嵌入在 `memory_manager.py` 和 `cli.py` 中。PR #5295 将这些逻辑抽离为通用接口，honcho 从此只是 `plugins/memory/honcho/` 下的一个普通插件，与其他记忆后端平等竞争。

## 二、通用插件系统：PluginManager 与 PluginContext

### 2.1 四层发现链

`PluginManager.discover_and_load()` 按顺序扫描四个来源：

| 优先级 | 来源 | 路径 | 说明 |
|--------|------|------|------|
| 1 | 捆绑插件 | `<repo>/plugins/<name>/` | 随 Hermes 发布，开箱即用 |
| 2 | 用户插件 | `~/.hermes/plugins/<name>/` | 用户手动安装，可覆盖捆绑插件 |
| 3 | 项目插件 | `./.hermes/plugins/<name>/` | 需 `HERMES_ENABLE_PROJECT_PLUGINS=1` 启用 |
| 4 | Pip 插件 | `hermes_agent.plugins` 入口点 | 通过 `pip install` 安装的第三方包 |

同名的后来源覆盖前者（last-writer-wins），即用户插件可以猴子补丁式地替换系统自带的任何捆绑插件。

发现阶段还会识别两种目录布局：

- **扁平布局**：`plugins/disk-cleanup/plugin.yaml` — 独立插件，key 为 `disk-cleanup`
- **分类布局**：`plugins/image_gen/openai/plugin.yaml` — 分类子插件，key 为 `image_gen/openai`

扫描时，`memory/`、`context_engine/`、`model-providers/` 和 `platforms/` 被顶层跳过——它们拥有自己独立的发现系统和生命周期管理。

### 2.2 PluginContext：插件与核心的契约

每个插件子目录必须包含 `plugin.yaml` 清单和 `__init__.py` 中的 `register(ctx)` 函数。核心调用 `register()` 时传入一个 `PluginContext` 实例，这是插件获取系统能力的唯一入口：

```python
class PluginContext:
    manifest: PluginManifest      # 插件的元数据（名称、版本、描述等）
    llm: PluginLlm               # 宿主拥有的 LLM 门面（受信任插件的特权能力）
```

通过 `ctx`，插件可以注册工具、生命周期钩子、CLI 子命令、平台适配器、提供者后端——全部通过标准方法调用，不需要触碰核心文件。

### 2.3 生命周期钩子

插件通过 `ctx.register_hook(hook_name, callback)` 在 Agent 运行时的关键节点注入逻辑。`VALID_HOOKS` 定义了 15 个标准钩子：

| 钩子 | 触发时机 | 说明 |
|------|---------|------|
| `pre_tool_call` | 工具执行前 | 可修改参数或拦截调用 |
| `post_tool_call` | 工具执行后 | 观察结果、触发副作用 |
| `pre_llm_call` | LLM API 调用前 | 修改消息列表或参数 |
| `post_llm_call` | LLM API 调用后 | 观察响应、触发日志 |
| `pre_api_request` | HTTP 请求发出前 | 修改请求体、URL、headers |
| `post_api_request` | HTTP 响应返回后 | 记录响应、触发重试 |
| `transform_llm_output` | LLM 输出返回给用户前 | 第一个返回非空字符串的钩子生效。适合词汇/人格转换 |
| `transform_terminal_output` | 终端输出渲染前 | 终端专属的格式转换 |
| `transform_tool_result` | 工具结果返回模型前 | 过滤、摘要、格式化工具输出 |
| `on_session_start` | 会话开始时 | 初始化会话级状态 |
| `on_session_end` | 会话结束时 | 清理、归档 |
| `on_session_finalize` | 会话最终化时 | 最后的持久化机会 |
| `on_session_reset` | 会话重置时 | 响应 `/reset` 命令 |
| `subagent_stop` | 子代理停止时 | 观察子代理结果 |
| `pre_gateway_dispatch` | 网关消息分发前 | 可返回 `{"action": "skip"}` 丢弃消息，或 `{"action": "rewrite", "text": "..."}` 重写消息 |

`pre_approval_request` 和 `post_approval_response` 是特殊的"仅观察"钩子——在用户审批危险命令前后触发，但插件不能否决或预应答审批（要阻止工具应使用 `pre_tool_call`）。

### 2.4 工具注册

插件通过 `ctx.register_tool()` 将自定义工具注入全局工具注册表，与内置工具平等对待：

```python
ctx.register_tool(
    name="kanban_create_board",
    toolset="kanban",
    schema={...},              # OpenAI function calling 格式
    handler=handle_create_board,
    requires_env=["KANBAN_API_KEY"],
    is_async=False,
    description="Create a new kanban board",
    emoji="📋",
    override=False,            # 设为 True 可替换同名内置工具
)
```

默认情况下，同名工具冲突时注册被拒绝。设置 `override=True` 可让插件替换内置实现（例如用自定义 CDP 方案替换默认浏览器工具）。

### 2.5 CLI 子命令注册

`ctx.register_cli_command()` 让插件生成 `hermes <subcommand>` 终端命令：

```python
ctx.register_cli_command(
    name="honcho",
    help="Manage honcho memory plugin",
    setup_fn=lambda subparser: subparser.add_argument("--reset"),
    handler_fn=honcho_command,
)
```

插件也可通过 `ctx.register_command()` 注册会话内斜杠命令（如 `/lcm`），这些命令在 CLI 对话和网关会话中均可用。名称冲突时，内置命令优先。

### 2.6 插件种类与加载策略

`PluginManifest.kind` 决定加载行为：

| kind | 说明 | 加载策略 |
|------|------|---------|
| `standalone` | 独立插件（默认） | 需用户在 `plugins.enabled` 中显式启用 |
| `backend` | 可插拔后端（如 image_gen） | 捆绑的自动加载，用户安装的需显式启用 |
| `exclusive` | 独占类别（memory） | 通过 `<category>.provider` 配置选择，通用扫描器跳过 |
| `platform` | 网关平台适配器（IRC 等） | 捆绑的自动加载，用户安装的需显式启用 |
| `model-provider` | 模型提供商 | 由 `providers/__init__.py` 独立发现，通用扫描器只记录清单 |

独占插件（`exclusive`）是最特殊的一类——同一时刻只允许一个实例，由类别专属的发现系统管理，通用 `PluginManager` 只记录元数据供内省使用，不加载模块。

## 三、核心政策：插件不得修改核心

这是 Hermes 插件系统的宪法级约束。以下文件被列为**不可修改**的白名单：

- `run_agent.py` — Agent 主循环
- `cli.py` — CLI 入口
- `gateway/run.py` — 网关入口
- `hermes_cli/main.py` — 主程序入口
- `agent/memory_manager.py` — 记忆编排器
- `tools/registry.py` — 工具注册表

任何需要在这些文件中添加插件特定逻辑的需求，都应该通过以下方式解决：

1. **扩展通用钩子表面** —— 在 `VALID_HOOKS` 中新增一个标准钩子名
2. **扩展 PluginContext 方法** —— 添加新的 `ctx.register_*()` 方法
3. **扩展抽象基类** —— 在 MemoryProvider / ContextEngine 等 ABC 中新增可选钩子

PR #5295 是"剥离而非嵌入"这一原则的模板操作：所有硬编码的 honcho 引用被替换为通用的 `sync_turn()` 调用、`on_memory_write()` 分发、`on_session_switch()` 通知。honcho 从此只是另一个插件——删除它不会让核心编译失败。

## 四、记忆提供者插件

### 4.1 独立的发现系统

记忆提供者使用 `plugins/memory/__init__.py` 中专用的发现系统，与通用 `PluginManager` 完全解耦：

```python
# 扫描两类目录
1. 捆绑提供者: plugins/memory/<name>/   (随 Hermes 发布)
2. 用户安装提供者: $HERMES_HOME/plugins/<name>/  (独立安装)

# 名称冲突时捆绑优先
```

发现时使用启发式文本扫描——检查 `__init__.py` 中是否包含 `"register_memory_provider"` 或 `"MemoryProvider"` 字符串——避免导入整个模块，降低兼容性风险。

### 4.2 加载机制

`load_memory_provider()` 支持两种注册模式：

1. **`register(ctx)` 模式**（推荐）：通过 `_ProviderCollector`（一个仿真的 `PluginContext`）捕获 `ctx.register_memory_provider()` 调用
2. **子类检测模式**（兜底）：遍历模块中所有 `MemoryProvider` 子类，尝试无参实例化

加载时还自动注册子模块以支持相对导入——例如 `holographic` 插件中的 `from .store import MemoryStore`。模块命名空间区分捆绑（`plugins.memory.<name>`）和用户安装（`_hermes_user_memory.<name>`），防止不同来源的同名插件在 `sys.modules` 中冲突。

### 4.3 CLI 命令策略

CLI 命令只为**当前激活的单个提供者**暴露：

```python
def discover_plugin_cli_commands() -> List[dict]:
    active_provider = _get_active_memory_provider()  # 从 memory.provider 配置读取
    # 只加载 active_provider/cli.py 中的 register_cli()
```

这意味着 `hermes honcho --reset` 只在用户配置 `memory.provider: honcho` 时可用。轻量扫描——只导入 `cli.py`，不需要初始化整个提供者 SDK。

### 4.4 内置提供者生态

`plugins/memory/` 目录下 8 个后端：

| 后端 | 定位 |
|------|------|
| **honcho** | 方言式用户建模，通过对话反差理解用户偏好 |
| **mem0** | 通用记忆层，分层存储 + 语义搜索 |
| **supermemory** | 云端记忆中枢，跨应用共享 |
| **byterover** | 面向开发者的代码记忆 |
| **hindsight** | 事后洞察引擎，从对话中提取结构化知识 |
| **holographic** | 全息记忆，多维度关联召回 |
| **openviking** | 开源 Viking 协议记忆后端 |
| **retaindb** | 基于 SQLite 的本地持久化记忆 |

所有外部后端通过 `MemoryManager.on_memory_write()` 钩子**镜像**内置记忆的每次写入，确保外部存储始终是内置状态的超集。`MemoryManager.add_provider()` 强制执行单一外部提供者限制——第二个外部提供者的注册请求被拒绝并记录警告，防止工具 schema 膨胀和语义冲突。

### 4.5 MemoryProvider 配置模式

`get_config_schema()` 和 `save_config()` 构成标准的零代码配置流程：

```python
def get_config_schema(self) -> List[Dict[str, Any]]:
    """返回配置字段定义，供 'hermes memory setup' 向导使用"""
    return [
        {"key": "api_key", "description": "API 密钥", "secret": True,  "required": True, "url": "https://..."},
        {"key": "mode",     "description": "运行模式", "secret": False, "required": False, "choices": ["cloud", "local"], "default": "cloud"},
    ]

def save_config(self, values: Dict[str, Any], hermes_home: str) -> None:
    """将非秘密配置写入提供者的原生位置"""
    # 例如写入插件目录下的 config.json
```

`hermes memory setup` 命令通过这两个方法自动生成交互式配置向导——新后端接入零手动配置步骤。

## 五、模型提供者插件

### 5.1 懒发现机制

模型提供者的注册由 `providers/__init__.py` 管理，采用**懒加载**策略——注册表 `_REGISTRY` 在首次调用 `get_provider_profile()` 或 `list_providers()` 时才填充：

```python
def get_provider_profile(name: str) -> ProviderProfile | None:
    if not _discovered:
        _discover_providers()        # 仅第一次触发
    canonical = _ALIASES.get(name, name)
    return _REGISTRY.get(canonical)
```

### 5.2 三层扫描顺序

`_discover_providers()` 按以下顺序导入，**后加载者覆盖先加载者**（last-writer-wins）：

```
1. 捆绑插件: plugins/model-providers/<name>/
2. 用户插件: $HERMES_HOME/plugins/model-providers/<name>/
3. 遗留模块: providers/<name>.py           (pkgutil.iter_modules 扫描)
```

第 3 步是向后兼容层——允许在可编辑安装中直接放置单文件 profile。新提供者应使用插件目录布局。

### 5.3 自注册模式

每个模型提供者插件在 `__init__.py` 顶层调用 `register_provider()`：

```python
# providers/__init__.py
def register_provider(profile: ProviderProfile) -> None:
    _REGISTRY[profile.name] = profile       # 后注册者替换先注册者
    for alias in profile.aliases:
        _ALIASES[alias] = profile.name
```

用户插件可以**替换**或**猴子补丁**任何捆绑的 profile——只需在同名目录下放入自己的 `__init__.py`，调用 `register_provider()` 时传入覆盖后的 `ProviderProfile`。别名系统让基模、莫愁等多种调用方式映射到同一后端。

## 七、政策：不再接受树内记忆提供者

2026 年 5 月，Hermes 项目宣布了一项硬性政策：

> **不再接受新的树内（in-tree）记忆提供者。** 任何包含 `plugins/memory/` 下新子目录的 PR 将被直接关闭。

未来的记忆后端必须以独立插件仓库的形式发布，通过 `pip install` 或 `hermes plugin add` 安装到 `~/.hermes/plugins/<name>/`。这一决策有三层考虑：

1. **降低核心维护负担**：每个后端有自己的 SDK 依赖、API 变更节奏和 bug 修复周期，捆绑在核心库中导致 Hermes 的发布被外部依赖阻塞
2. **赋予后端作者自主发布权**：独立仓库可以按自己的节奏发版、做 breaking changes、独立处理 issue
3. **保持核心纯净**：这与"插件不得修改核心"的原则一脉相承——核心代码规模不随生态扩张而膨胀

## 九、设计模式提炼

| 模式 | 实现 | 解决的问题 |
|------|------|-----------|
| 门面隔离 | `PluginContext` 是插件访问系统的唯一入口 | 插件不耦合核心内部实现 |
| 多级发现 | 捆绑 → 用户 → 项目 → Pip，后覆盖前 | 第三方可替换任何系统插件 |
| 懒加载 | 模型提供者在首次查询时填充注册表 | 启动零开销，按需初始化 |
| 分类治理 | memory/context_engine/model-providers 有独立发现 | 不同生命周期需求不同策略 |
| 独占限制 | `MemoryManager` 拒绝第二个外部提供者 | 防止 schema 膨胀和语义冲突 |
| 故障隔离 | 每个钩子的 try/except 包裹 | 一个插件的异常不中断 Agent |
| 启发式扫描 | 文本匹配而非导入决定是否为记忆插件 | 降低兼容性风险 |
| 树外政策 | 不再接受新树内记忆后端 | 核心规模不随生态膨胀 |
| 配置自描述 | `get_config_schema()` + `save_config()` | 零代码交互式配置向导 |

## 十、总结

Hermes Agent 的插件系统是一个教科书级的"核心-插件分离"架构实践。它通过 `PluginContext` 门面将系统能力以统一契约暴露给插件，通过四层发现链实现用户级、项目级、系统级的替换能力，并通过 `exclusive`、`backend`、`model-provider` 等种类标签实现灵活的加载策略。最值得学习的是它的"核心瘦身"纪律——PR #5295 宁可移除 95 行工作代码也要保持核心的通用性，这种设计约束在长期维护中产生的复利效应远超过短期便利。
