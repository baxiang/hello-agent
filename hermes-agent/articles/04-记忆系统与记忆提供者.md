# Hermes Agent 记忆系统与记忆提供者

> **项目**: [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) | **版本**: v0.15.1
> **核心文件**: `agent/memory_provider.py` (~300 行) · `agent/memory_manager.py` (~400 行)

---

## 一、为什么需要记忆系统

LLM 本身是无状态的——每次对话从零开始。一个真正有用的 Agent 必须跨会话保留知识：记住用户偏好、累积项目经验、追踪长期目标。Hermes Agent 的记忆系统设计了**双轨架构**：内置的轻量文件存储（MEMORY.md / USER.md）保证开箱即用，外部插件后端（honcho、mem0 等）提供专业级语义召回。两轨由同一个 `MemoryManager` 编排，对上层循环透明。

---

## 二、MemoryProvider 抽象基类

`agent/memory_provider.py` 定义了所有记忆后端的契约。核心思想：**每个提供者是一个自包含的记忆微服务**，拥有独立的生命周期、工具 schema 和召回逻辑。

### 2.1 核心生命周期方法

```python
class MemoryProvider(ABC):
    @property
    @abstractmethod
    def name(self) -> str: ...

    @abstractmethod
    def is_available(self) -> bool:
        """仅检查配置和凭据，不做网络调用"""

    @abstractmethod
    def initialize(self, session_id: str, **kwargs) -> None:
        """连接后端、创建资源、启动后台线程"""

    def system_prompt_block(self) -> str:
        """注入系统提示的静态文本（如后端使用说明）"""

    def prefetch(self, query: str, *, session_id: str = "") -> str:
        """每轮 API 调用前的背景召回，应快速返回缓存结果"""

    def queue_prefetch(self, query: str, *, session_id: str = "") -> None:
        """为本轮排队后台召回，下一轮 prefetch() 消费"""

    def sync_turn(self, user_content, assistant_content,
                  *, session_id="", messages=None) -> None:
        """每轮完成后持久化，应非阻塞"""

    @abstractmethod
    def get_tool_schemas(self) -> List[Dict]:
        """暴露给模型的工具 schema（OpenAI function calling 格式）"""

    def handle_tool_call(self, tool_name, args, **kwargs) -> str:
        """分发工具调用，返回 JSON 字符串"""

    def shutdown(self) -> None:
        """刷新队列、关闭连接"""
```

`initialize()` 的 `kwargs` 设计值得细看。它**总是**包含 `hermes_home` 和 `platform`，**可能**包含 `agent_context`、`agent_identity`、`agent_workspace`、`parent_session_id`、`user_id`、`user_id_alt`。这种"必选 + 可选"模式让提供者可以按需获取上下文，而不必导入全局状态。特别值得注意的是 `agent_context`——其值为 `"primary"` / `"subagent"` / `"cron"` / `"flush"`，提供者应跳过非 primary 上下文的写入，否则 cron 的系统提示会污染用户画像。

### 2.2 可选钩子

除了核心生命周期，`MemoryProvider` 还定义了 6 个可选钩子，覆盖 Agent 运行时的关键事件：

| 钩子 | 触发时机 | 典型用途 |
|------|---------|---------|
| `on_turn_start(turn_number, message, **kw)` | 每轮开始 | 轮次计数、周期性维护 |
| `on_session_end(messages)` | 会话结束（CLI 退出、/reset、网关超时） | 端点事实提取、总结 |
| `on_session_switch(new_session_id, parent_session_id, reset, **kw)` | session_id 中途切换 | 刷新缓存状态，使后续写入落在正确会话 |
| `on_pre_compress(messages) -> str` | 上下文压缩前 | 从即将丢弃的消息中提取洞察 |
| `on_memory_write(action, target, content, metadata)` | 内置记忆工具写入时 | 镜像写入到外部后端 |
| `on_delegation(task, result, child_session_id, **kw)` | 子代理完成后 | 父代理观察委派结果 |

`on_session_switch` 的设计最精巧。它在 `/resume`、`/branch`、`/reset`、`/new` 以及上下文压缩时触发——任何重新赋值 `AIAgent.session_id` 但不销毁提供者的路径。`reset=True` 表示全新对话（提供者应清空累积缓冲区），`reset=False` 表示逻辑对话在新区 ID 下继续（如 /resume、压缩）。

`on_memory_write` 是外部后端的核心同步通道。当内置 memory 工具执行 `add`/`replace`/`remove` 操作时，`MemoryManager` 调用所有外部提供者的此钩子，使外部后端始终与内置记忆保持一致。`metadata` 参数携带结构化溯源信息：`write_origin`、`execution_context`、`session_id`、`platform`、`tool_name` 等。

### 2.3 配置发现

```python
def get_config_schema(self) -> List[Dict]:
    """返回配置字段定义，供 'hermes memory setup' 向导使用"""

def save_config(self, values: Dict, hermes_home: str) -> None:
    """将非秘密配置写入提供者原生位置"""
```

`get_config_schema()` 的每个字段可声明 `key`、`description`、`secret`（是否写入 .env）、`required`、`default`、`choices`、`url`（凭据获取地址）和 `env_var`。这让 `hermes memory setup` 命令能自动生成交互式配置向导，零代码接入新后端。

## 三、MemoryManager 编排器

`agent/memory_manager.py` 是记忆系统唯一的上层入口，`run_agent.py` 只与它交互。它编排所有注册提供者的生命周期，并处理上下文围栏。

### 3.1 单一外部提供者限制

```python
def add_provider(self, provider: MemoryProvider) -> None:
    is_builtin = provider.name == "builtin"
    if not is_builtin:
        if self._has_external:
            logger.warning(
                "Rejected memory provider '%s' — external provider '%s' is "
                "already registered.", provider.name, existing,
            )
            return
        self._has_external = True
```

这是架构级的硬约束：**同一时刻只允许一个外部提供者**。内置提供者（name="builtin"）始终可用，但外部后端互斥。原因有二：

1. **工具 schema 膨胀**：每个提供者可能注册多个工具（recall、search、manage 等），多后端叠加会挤占上下文窗口
2. **语义冲突**：两个记忆后端对同一查询返回矛盾结果，模型无法仲裁

### 3.2 工具名路由

```python
self._tool_to_provider: Dict[str, MemoryProvider] = {}

# 注册时索引
for schema in provider.get_tool_schemas():
    tool_name = schema.get("name", "")
    self._tool_to_provider[tool_name] = provider

# 调用时路由
def handle_tool_call(self, tool_name, args, **kwargs) -> str:
    provider = self._tool_to_provider.get(tool_name)
    return provider.handle_tool_call(tool_name, args, **kwargs)
```

每个工具名唯一映射到一个提供者。同名冲突时，先注册者赢，后注册者被跳过并记录警告。

### 3.3 故障隔离

`MemoryManager` 的所有编排方法遵循同一模式：**一个提供者的失败永远不阻塞其他提供者**。

```python
def prefetch_all(self, query, *, session_id="") -> str:
    parts = []
    for provider in self._providers:
        try:
            result = provider.prefetch(query, session_id=session_id)
            if result and result.strip():
                parts.append(result)
        except Exception as e:
            logger.debug("... prefetch failed (non-fatal): %s", e)
    return "\n\n".join(parts)
```

每个提供者调用都被 try/except 包裹，异常降级为 debug/warning 日志。`sync_all`、`queue_prefetch_all`、`on_turn_start`、`on_session_switch`、`on_pre_compress`、`on_delegation`、`shutdown_all` 全部遵循此模式。

### 3.4 on_memory_write 跳过内置提供者

```python
def on_memory_write(self, action, target, content, metadata=None) -> None:
    for provider in self._providers:
        if provider.name == "builtin":
            continue  # 内置提供者是写入的源头，不需要镜像
        provider.on_memory_write(action, target, content, metadata=...)
```

`on_memory_write` 的语义是"内置记忆工具写入时通知外部后端"。内置提供者本身是写入的发起者，如果也通知它，就是自我通知——所以跳过。

### 3.5 签名兼容性检测

```python
@staticmethod
def _provider_sync_accepts_messages(provider: MemoryProvider) -> bool:
    signature = inspect.signature(provider.sync_turn)
    params = list(signature.parameters.values())
    if any(p.kind == inspect.Parameter.VAR_KEYWORD for p in params):
        return True
    return "messages" in signature.parameters
```

`sync_turn` 的 `messages` 参数是后期新增的。为保持向后兼容，`MemoryManager` 运行时检查提供者的 `sync_turn` 签名：如果接受 `**kwargs` 或显式声明 `messages` 参数，才传入完整消息列表，否则只传 `user_content` 和 `assistant_content`。同样的检测逻辑也用于 `on_memory_write` 的 `metadata` 参数传递方式（keyword / positional / legacy 三种模式）。

## 四、上下文围栏机制

记忆上下文被注入到对话中时，必须与用户输入明确区分，否则模型会混淆"回忆起的旧信息"和"用户刚刚说的话"。Hermes 用 XML 标签围栏解决这个问题。

### 4.1 围栏格式

```python
def build_memory_context_block(raw_context: str) -> str:
    return (
        "<memory-context>\n"
        "[System note: The following is recalled memory context, "
        "NOT new user input. Treat as authoritative reference data — "
        "this is the agent's persistent memory and should inform all responses.]\n\n"
        f"{clean}\n"
        "</memory-context>"
    )
```

三重防护：
1. `<memory-context>` 标签划定边界
2. System note 语气指令：**这不是新输入，是记忆**
3. `sanitize_context()` 先清除提供者返回内容中可能残留的旧围栏标签（防止嵌套注入）

### 4.2 StreamingContextScrubber：流式清洗状态机

问题：模型流式输出时，`<memory-context>` 标签可能被拆分到多个 chunk 中。正则表达式无法跨 chunk 匹配，导致标签和记忆内容泄露到用户界面。

```python
class StreamingContextScrubber:
    def __init__(self):
        self._in_span: bool = False    # 是否在记忆区间内
        self._buf: str = ""            # 暂存可能是标签片段的尾部
        self._at_block_boundary: bool = True  # 是否在块边界

    def feed(self, text: str) -> str:
        """返回可见部分，暂存可能是标签片段的尾部"""

    def flush(self) -> str:
        """流结束时：如果仍在未关闭的区间内，丢弃内容（安全优先）"""
```

状态机工作流：

```
普通文本 → 发现 <memory-context> → 进入 span（丢弃内容）
                                    ↓
                              发现 </memory-context> → 退出 span（继续输出）
```

关键细节：
- **跨 chunk 标签重组**：`_max_partial_suffix()` 检测缓冲区尾部是否可能是标签前缀（如 `"<memory"` 不完整），暂存到 `_buf`，与下一个 chunk 拼接后再判断
- **块边界检测**：`_is_block_boundary()` 和 `_has_block_opener_suffix()` 确保 `<memory-context>` 只在行首被识别，防止正文中的同名文本被误判
- **安全优先的 flush**：如果流结束时仍在 span 内（未关闭），剩余内容**全部丢弃**。泄露部分记忆比截断回答更危险

### 4.3 sanitize_context：一次性清洗

```python
_FENCE_TAG_RE = re.compile(r'</?\s*memory-context\s*>', re.IGNORECASE)
_INTERNAL_CONTEXT_RE = re.compile(
    r'<\s*memory-context\s*>[\s\S]*?</\s*memory-context\s*>', re.IGNORECASE
)
_INTERNAL_NOTE_RE = re.compile(
    r'\[System note:\s*The following is recalled memory context[^\]]*\.\]\s*',
    re.IGNORECASE,
)

def sanitize_context(text: str) -> str:
    text = _INTERNAL_CONTEXT_RE.sub('', text)
    text = _INTERNAL_NOTE_RE.sub('', text)
    text = _FENCE_TAG_RE.sub('', text)
    return text
```

用于非流式场景（提供者返回值、工具结果等）的清洗。按三层递进：先移除完整围栏块，再移除 System note，最后移除残留标签。

## 五、内置记忆：MEMORY.md 与 USER.md

内置提供者（name="builtin"）是最简单、最可靠的记忆后端——纯文件存储，零网络依赖：

- **MEMORY.md**：Agent 的个人笔记，记录任务经验、项目知识、操作诀窍
- **USER.md**：用户档案，记录偏好、习惯、沟通风格

每次 Agent 调用 `memory` 工具执行 `add`/`replace`/`remove` 操作时，直接读写这两个 Markdown 文件。简单、可审计、可版本控制。

## 六、外部后端生态

`plugins/memory/` 目录下 8 个外部提供者，各有专长：

| 后端 | 定位 |
|------|------|
| **honcho** | 方言式用户建模（Dialectic User Modeling），通过对话反差理解用户 |
| **mem0** | 通用记忆层，分层存储 + 语义搜索 |
| **supermemory** | 云端记忆中枢，跨应用共享 |
| **byterover** | 面向开发者的代码记忆 |
| **hindsight** | 事后洞察引擎，从对话中提取结构化知识 |
| **holographic** | 全息记忆，多维度关联召回 |
| **openviking** | 开源 Viking 协议记忆后端 |
| **retaindb** | 基于 SQLite 的本地持久化记忆 |

所有外部后端通过 `on_memory_write` 钩子**镜像**内置记忆的每次写入，确保外部存储始终是内置状态的超集。这意味着用户可以随时切换后端而不丢失已有记忆。

## 七、政策：不再接受树内提供者

截至 2026 年 5 月，Hermes 项目宣布**不再接受新的树内记忆提供者**。新的后端必须作为独立插件仓库发布，通过 `pip install` 或 `hermes plugin add` 安装。这一决策与核心设计哲学一致：**插件不得修改核心**。将记忆后端从核心代码库中剥离，既降低了维护负担，也给了后端作者独立的发布节奏。

## 八、总结：设计模式提炼

| 模式 | 实现 | 解决的问题 |
|------|------|-----------|
| 双轨记忆 | 内置文件 + 外部插件 | 开箱即用与专业级召回兼得 |
| 单一外部限制 | `add_provider()` 拒绝第二个外部提供者 | 防止 schema 膨胀和语义冲突 |
| 故障隔离 | 每个提供者调用 try/except | 一个后端崩溃不影响其他 |
| 上下文围栏 | `<memory-context>` XML 标签 | 防止模型混淆记忆与新输入 |
| 流式清洗状态机 | `StreamingContextScrubber` | 防止跨 chunk 标签泄露 |
| 签名兼容性检测 | `inspect.signature()` 运行时检查 | 新参数向后兼容旧提供者 |
| 写入镜像 | `on_memory_write` 跳过 builtin | 外部后端始终同步内置状态 |
| 树外政策 | 不再接受新树内提供者 | 核心简洁，插件独立发布 |
