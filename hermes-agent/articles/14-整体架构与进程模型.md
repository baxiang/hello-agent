## 一、项目概述

Hermes Agent 是 Nous Research 团队推出的**自演进 AI Agent**——目前唯一内置完整学习闭环的通用 Agent 框架。截至 v0.15.1，项目已获得 **173k+ Stars、29k+ Forks**，累计近万次提交，是 GitHub 上最活跃的 Agent 开源项目之一。

与绝大多数 Agent 框架不同，Hermes Agent 将"自我改进"作为一等公民而非事后补丁：它包括**经验驱动的技能创建**、**使用中自动优化**、**跨会话记忆持久化**、以及**周期性知识整理提示**（nudge）。同时，它支持 20+ 模型提供商、8 种记忆后端、6+ 消息平台，MIT 协议开源。

## 二、三种核心设计哲学

贯穿整个 Hermes Agent 代码仓库的设计哲学只有三条，但每一条都深刻影响了代码结构：

### 2.1 注册 ≠ 暴露

工具被注册到全局 `Registry`（`tools/registry.py`）后，**并不会自动对模型可见**。必须显式分配到对应的 `Toolset`（定义在 `toolsets.py`），再由 `model_tools.py` 从 Toolset 中收集工具 schema，最终注入到 LLM 请求中。

```python
# 注册（全局可见，被 Agent 内部调用）
@register_tool(name="bash")
def run_bash(command: str) -> str:
    ...

# 暴露（模型可见——必须在 toolsets.py 的某个 Toolset 中声明）
TOOLSET_DEV = Toolset(
    name="development",
    tools=["bash", "read", "write", "edit", "glob", "grep"],
)
```

这种"注册-分配"两层模型的意义在于：**安全隔离**。即使是内部必须使用的工具（如 `skill_load`），也可以选择不对模型暴露，防止模型通过工具调用绕过安全策略。

### 2.2 插件不得修改核心

插件系统（`plugins/`）遵循严格的"扩展面"（plugin surface）设计——核心代码提供 hook 点，插件在这些 hook 点上注册回调。**核心源码中不存在任何 `if plugin_X_enabled:` 的分支代码**。

所有插件交互通过监听 `PluginEvent` 枚举实现：
- `AGENT_INIT` — Agent 初始化完成
- `TOOLS_DISCOVERED` — 工具发现完毕
- `MESSAGE_RECEIVED` — 收到用户消息
- `MESSAGE_SENT` — Agent 回复发送
- `CONVERSATION_ENDED` — 会话结束

这个设计使第三方可以在不触碰上游核心的前提下扩展 Agent 行为，大大降低了合并冲突和维护成本。

### 2.3 缓存完整性

**会话内绝不修改已组装的 Toolset 和 System Prompt**。修改工具列表或系统提示词会使上游 Prompt Cache 失效——对使用 Anthropic Claude 的用户，这意味着一轮对话的成本可能从 $0.01 飙升至 $0.50+。

为了实现这一点，`system_prompt.py` 将提示词分为三层：`stable`（进程生命周期内不变）、`context`（跨会话可变）、`volatile`（每次会话重建）。`toolsets.py` 则在 Agent 初始化时一次性冻结 Toolset 快照，会话过程中不再修改。

## 四、三种进程模型

Hermes Agent 不是一个"一种启动方式走天下"的项目。根据使用场景，它提供三种截然不同的进程模型：

### 4.1 CLI 模式：单进程 prompt_toolkit

```
┌─────────────────────────────────┐
│  hermes (Shell Wrapper)         │
│    └─ python cli.py chat        │
│         ├─ AIAgent              │
│         ├─ prompt_toolkit loop  │
│         └─ stdout 输出          │
└─────────────────────────────────┘
```

这是最基础的模式。`hermes` shell 脚本检测虚拟环境后调用 `cli.py chat`，启动一个 **Python 单进程**。输入由 `prompt_toolkit` 驱动，支持多行编辑、历史记录、语法高亮和自动补全。输出直接写入 stdout，流式 token 被实时渲染。

```python
# hermes_cli/commands/chat.py 简化逻辑
def chat_cmd():
    agent = AIAgent.from_config(load_cli_config())
    session = prompt_toolkit.PromptSession()
    while True:
        user_input = session.prompt("> ")
        agent.conversation_loop(user_input)
```

### 4.2 TUI 模式：双进程 JSON-RPC

```
┌──────────────────────┐     stdio JSON-RPC     ┌──────────────────────┐
│  ui-tui (Node.js)    │ ◄──────────────────► │  tui_gateway (Python) │
│  ┌────────────────┐  │                        │  ┌────────────────┐  │
│  │ Ink/React 渲染  │  │  "render" ──────────► │  │ JSON-RPC Server│  │
│  │ 终端 ANSI 组件   │  │ ◄────────── "output"  │  │                │  │
│  │                │  │                        │  │ AIAgent        │  │
│  │ 用户输入捕获     │  │  "user_message" ────► │  │                │  │
│  └────────────────┘  │                        │  └────────────────┘  │
└──────────────────────┘                        └──────────────────────┘
```

TUI 模式是一个**双进程架构**：

- **前端进程**：Node.js 运行 `ui-tui/`（Ink/React），负责终端渲染。Ink 是一个使用 React 组件模型渲染终端 UI 的框架，支持 Flexbox 布局、颜色主题、动画效果。
- **后端进程**：Python 运行 `tui_gateway/server.py`，启动 JSON-RPC 服务器，通过 stdio 管道与前端通信。

通信协议是简化版的 JSON-RPC 2.0：
```
→ {"jsonrpc": "2.0", "method": "user_message", "params": {"text": "hello"}, "id": 1}
← {"jsonrpc": "2.0", "result": {"stream": "Hello! How can I help?"}, "id": 1}
```

这种分离的好处是：前端可以用现代 Web 技术栈（React/TypeScript），后端保持 Python 生态，二者通过标准协议解耦。TUI 模式下用户获得完整的流式输出、彩色语法高亮、以及会话历史侧栏。

### 4.3 Gateway 模式：单进程多线程

```
┌──────────────────────────────────────────────┐
│  gateway/main.py (单进程)                      │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐      │
│  │ Telegram │ │ Discord  │ │ Slack    │ ...  │
│  │ Thread   │ │ Thread   │ │ Thread   │      │
│  └────┬─────┘ └────┬─────┘ └────┬─────┘      │
│       │            │            │            │
│       └────────────┼────────────┘            │
│                    ▼                          │
│           ┌────────────────┐                 │
│           │  Agent Pool    │                 │
│           │  (per-session  │                 │
│           │   AIAgent 实例) │                 │
│           └────────────────┘                 │
│                    │                          │
│                    ▼                          │
│           ┌────────────────┐                 │
│           │  Memory/State  │                 │
│           │  (跨会话共享)    │                 │
│           └────────────────┘                 │
└──────────────────────────────────────────────┘
```

Gateway 模式用**单进程多线程**架构同时服务多平台。`gateway/main.py` 启动后为每个平台初始化一个 listener 线程（Telegram Bot、Discord Client、Slack App 等），所有线程共享同一个 Agent Pool 和状态存储。

关键设计：
- **每会话独立 Agent 实例**：不同用户/会话获得独立的 `AIAgent` 实例，避免跨用户状态污染。
- **共享服务单例**：记忆后端、技能存储、配置管理器是进程级单例，节省内存和连接数。
- **线程安全隔离**：工具执行通过消息队列同步，确保同一 Agent 实例的 API 调用序列化。

Gateway 模式还集成了内置定时器（`cron/`），支持自然语言描述的定时任务（如"每天早上 9 点生成日报并发送到 Telegram"）。

## 五、依赖链：严格的导入顺序

为防止循环导入，Hermes Agent 设定了一条严格的依赖链——下层绝不引用上层：

```
tools/registry.py          ← 零依赖，纯字典注册
    ↓
tools/*.py                 ← 各工具实现，仅引用 registry + stdlib
    ↓
toolsets.py                ← 仅引用 tools/registry
    ↓
model_tools.py             ← 引用 tools/* + toolsets.py
    ↓
run_agent.py / cli.py      ← 顶层，引用以上所有
```

这条链是如何被执行的：

```python
# tools/registry.py — 零外部依赖
_tool_registry: dict[str, ToolEntry] = {}

def register_tool(name: str) -> Callable:
    def decorator(fn):
        _tool_registry[name] = ToolEntry(fn=fn, ...)
        return fn
    return decorator

# model_tools.py — 依赖所有 tools/*
from tools.registry import get_all_tools
from toolsets import get_toolset_for_session

def collect_model_tools(toolset_name: str) -> list[dict]:
    toolset = get_toolset_for_session(toolset_name)
    return [_tool_registry[name].schema for name in toolset.tool_names]

# run_agent.py — 依赖 model_tools.py 但不被下层引用
from model_tools import collect_model_tools
```

违反这条链的 PR 会在 CI 中被一个专门的循环导入检查步骤拦截（`python -c "import <module>"` 的批量执行）。

## 六、三种配置加载器

不同入口使用不同的配置加载策略：

| 加载器 | 入口 | 加载方式 | 特点 |
|--------|------|---------|------|
| `load_cli_config()` | `hermes_cli/` | 优先 CLI 参数 → 环境变量 → YAML 文件 | 支持命令行覆盖，用于 `hermes chat`、`hermes model` 等命令 |
| `load_config()` | 子命令批量操作 | YAML 文件 + 可选覆盖 | 用于 `hermes batch-run`、`hermes trajectory` 等批处理 |
| 直接 YAML 加载 | `gateway/` | 纯 YAML 文件 | 最稳定——Gateway 长期运行，不依赖 CLI 参数 |

设计原因：Gateway 作为长期运行的生产进程，需要完全可复现的配置——不能受临时环境变量或命令行参数干扰。而 CLI 模式恰好需要灵活性——用户可能只想临时切换模型：`hermes --model openrouter:claude-sonnet-4-20250514`。

## 九、设计启示

回顾 Hermes Agent 的整体架构，有几个值得关注的工程决策：

1. **宁可复制代码也不要循环导入**。`agent/` 目录下 60+ 模块看似冗余，但每个模块职责单一、依赖清晰。对比将全部逻辑塞入一个巨大核心模块的做法，这种"激进模块化"在 9,000+ 提交的历史中验证了其可维护性。

2. **用 Registry 模式替代直接导入**。工具、浏览器、图像生成、TTS、转录、记忆——所有这些可替换组件都遵循 `XxxProvider` ABC + `XxxRegistry` 的路由模式。核心代码不直接 import 任何具体实现，完全通过 Registry 查找。这是一种"编译时无依赖、运行时晚绑定"的架构。

3. **进程模型分层是产品演进的必然结果**。Hermes 从最初的纯 CLI（单进程）演进到双进程 TUI（更好的 UX），再发展到 Gateway（多平台服务）。每一层进程模型都是对前一层的扩展而非替代——三种模型共存，服务不同的使用场景。

4. **"缓存完整性"不是性能优化，是成本控制**。Anthropic 的 Prompt Cache 按 token 计费——对于每天数万次对话的 Gateway，缓存命中率 90% vs 60% 的差别可能是每月数千美元的成本差异。这就是为什么 `system_prompt.py` 和 `toolsets.py` 中有大量不易察觉的"冻结"逻辑。
