# Hermes Agent 子代理委派系统深度解析

> **项目**: [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) | **版本**: v0.15.1
> **核心文件**: `tools/delegate_tool.py` (~2800 行) | **分析日期**: 2026-05-29

---

## 一、架构概述：可组合的并行计算单元

Hermes Agent 的子代理委派系统不是一个简单的"函数调用转发器"，而是一套**进程内多 Agent 编排框架**。`delegate_task` 工具在父代理的对话循环中生成独立的 `AIAgent` 子实例，每个子代理拥有完全隔离的上下文、受限的工具集和独立的终端会话。父代理在委派期间阻塞等待，直到所有子代理完成并返回汇总结果。

核心设计原则：**父代理只看到委派调用和摘要结果，永远不接触子代理的中间工具调用或推理过程**。这意味着一个 `delegate_task` 调用在父代理的对话历史中只占一条 tool_call + 一条 tool_result，无论子代理内部执行了多少步操作。

```python
child = AIAgent(
    enabled_toolsets=child_toolsets,       # 1. 受限工具集
    ephemeral_system_prompt=child_prompt,   # 2. 聚焦系统提示词
    skip_context_files=True,               # 3. 跳过上下文文件
    skip_memory=True,                      # 4. 跳过记忆加载
    clarify_callback=None,                 # 5. 无用户交互能力
    iteration_budget=None,                 # 6. 独立迭代预算
)
```

每个子代理获得的隔离保障：

- **全新对话**：不继承父代理的历史消息
- **独立 task_id**：拥有自己的终端会话和文件操作缓存
- **受限工具集**：可配置，且始终剥离被屏蔽的工具
- **聚焦系统提示词**：从 `goal + context` 参数动态构建

## 二、DELEGATE_BLOCKED_TOOLS：能力边界的硬约束

```python
DELEGATE_BLOCKED_TOOLS = frozenset([
    "delegate_task",   # 禁止递归委派 -- 防止无限生成子代理
    "clarify",         # 禁止用户交互 -- 子代理不能打断用户
    "memory",          # 禁止写入共享 MEMORY.md -- 防止记忆污染
    "send_message",    # 禁止跨平台副作用 -- 子代理不能发 Telegram/Discord 消息
    "execute_code",    # 禁止代码执行 -- 子代理应逐步推理，而非写脚本
])
```

这五个工具的屏蔽不仅是功能限制，更是**安全边界**：

| 工具 | 屏蔽原因 | 不屏蔽的后果 |
|------|---------|-------------|
| `delegate_task` | 递归生成不可控 | 子代理生成子代理，深度无限，资源耗尽 |
| `clarify` | 用户无法与子代理交互 | 子代理挂起等待用户输入，父代理永远阻塞 |
| `memory` | 共享记忆文件缺乏并发控制 | 多个子代理同时写入 MEMORY.md，数据损坏 |
| `send_message` | 跨平台副作用不可预测 | 子代理在用户不知情时发送消息 |
| `execute_code` | 子代理应逐步推理 | 子代理写脚本执行，绕过审批流程 |

`_strip_blocked_tools()` 函数在构建子代理工具集时，直接移除包含这些工具的整个工具集（`delegation`、`clarify`、`memory`、`code_execution`），而非单独剥离工具——这是"注册 != 暴露"哲学的延伸。

## 三、两种委派形态：单任务与批量并行

### 3.1 单任务模式

```python
delegate_task(
    goal="分析 src/auth.py 的安全漏洞",
    context="这是一个 OAuth2 实现，关注 token 泄露风险",
    toolsets=["terminal", "file", "web"],
)
```

单任务直接在主线程执行 `_run_single_child()`，无线程池开销。父代理阻塞直到子代理返回结果。

### 3.2 批量并行模式

```python
delegate_task(
    tasks=[
        {"goal": "搜索 CVE-2024-* 相关漏洞", "context": "...", "toolsets": ["web"]},
        {"goal": "审计依赖项许可证合规性", "context": "...", "toolsets": ["terminal", "file"]},
        {"goal": "检查代码中的硬编码密钥", "context": "...", "toolsets": ["terminal", "file"]},
    ]
)
```

批量模式使用 `ThreadPoolExecutor` 并行执行所有子代理，并发上限由 `delegation.max_concurrent_children` 控制（默认 3）。超出上限的任务直接拒绝，不排队：

```python
max_children = _get_max_concurrent_children()
if len(tasks) > max_children:
    return tool_error(
        f"Too many tasks: {len(tasks)} provided, "
        f"but max_concurrent_children is {max_children}."
    )
```

关键实现细节：批量模式下父代理使用 `concurrent.futures.wait(FIRST_COMPLETED)` 以 0.5 秒轮询，而非 `as_completed()`——后者会阻塞到所有 future 完成，当子代理卡住时父代理永远无法响应中断信号。

## 四、角色体系：Leaf 与 Orchestrator

### 4.1 Leaf 角色（默认）

`role="leaf"` 是子代理的默认角色。Leaf 工作器：

- 不能调用 `delegate_task`（工具集被 `_strip_blocked_tools` 剥离）
- 不能调用 `clarify`、`memory`、`send_message`、`execute_code`
- 系统提示词聚焦于单一任务的完成

### 4.2 Orchestrator 角色

`role="orchestrator"` 让子代理保留 `delegate_task` 工具，能够生成自己的工作器：

```python
if effective_role == "orchestrator" and "delegation" not in child_toolsets:
    child_toolsets.append("delegation")
```

Orchestrator 角色的系统提示词包含委派指导——何时委派（可并行的独立子任务、推理密集型子任务），何时不委派（单步机械操作、两三个工具调用即可完成的任务、将整个目标透传给一个工作器）。

### 4.3 深度限制

深度体系通过 `_delegate_depth` 属性在代理链中传递：

```
depth=0  父代理 (用户直接交互)
depth=1  第一层子代理 (leaf 或 orchestrator)
depth=2  第二层子代理 (仅当 max_spawn_depth >= 2 且父为 orchestrator)
depth=3  绝对上限 (_MAX_SPAWN_DEPTH_CAP = 3)
```

深度检查在 `delegate_task` 入口处执行：

```python
depth = getattr(parent_agent, "_delegate_depth", 0)
max_spawn = _get_max_spawn_depth()  # 从 config.yaml 读取，默认 1
if depth >= max_spawn:
    return json.dumps({"error": "Delegation depth limit reached ..."})
```

关键常量：

- `MAX_DEPTH = 1`：默认扁平结构，父 -> 子，子不能继续委派
- `_MAX_SPAWN_DEPTH_CAP = 3`：硬编码上限，防止配置错误导致无限深度
- `_MIN_SPAWN_DEPTH = 1`：最小值，确保至少一层委派

角色降级逻辑：即使调用方请求 `role="orchestrator"`，如果深度已达上限或 `orchestrator_enabled` 为 False，角色也会静默降级为 `leaf`：

```python
orchestrator_ok = _get_orchestrator_enabled() and child_depth < max_spawn
effective_role = role if (role == "orchestrator" and orchestrator_ok) else "leaf"
```

## 五、子代理审批回调：线程安全的关键难题

### 5.1 问题根源

这是 `delegate_tool.py` 中最精妙的设计之一。问题链条如下：

1. 子代理在 `ThreadPoolExecutor` 的 worker 线程中运行
2. CLI 的交互式审批回调存储在 `threading.local()` 中（`tools/terminal_tool.py`）
3. Worker 线程**不继承**父线程的 `threading.local()` 状态
4. 没有回调时，`prompt_dangerous_approval()` 回退到 `input()`
5. `input()` 从 worker 线程读取 stdin，与父代理的 `prompt_toolkit` TUI **死锁**

### 5.2 解决方案

通过 `ThreadPoolExecutor(initializer=_set_subagent_approval_cb, initargs=(cb,))` 在每个 worker 线程启动时安装非交互式回调：

```python
_timeout_executor = ThreadPoolExecutor(
    max_workers=1,
    initializer=_set_subagent_approval_cb,
    initargs=(_get_subagent_approval_callback(),),
)
```

两种回调策略：

```python
def _subagent_auto_deny(command, description, **kwargs) -> str:
    logger.warning(
        "Subagent auto-denied dangerous command: %s (%s). "
        "Set delegation.subagent_auto_approve: true to allow.",
        command, description,
    )
    return "deny"

def _subagent_auto_approve(command, description, **kwargs) -> str:
    logger.warning(
        "Subagent auto-approved dangerous command: %s (%s)",
        command, description,
    )
    return "once"
```

选择逻辑由 `delegation.subagent_auto_approve` 配置项控制：

- `false`（默认） -> `_subagent_auto_deny`：安全优先，子代理看到拒绝后可以尝试替代方案
- `true` -> `_subagent_auto_approve`：YOLO 模式，适用于 cron/batch 场景

两种回调都发出 `logger.warning` 用于审计。网关会话不受影响，因为它们通过 `tools/approval.py` 的每会话队列解析审批，而非依赖 TLS 回调。

## 六、全局运行时状态：可观测性与控制

### 6.1 生成暂停机制

```python
_spawn_paused: bool = False

def set_spawn_paused(paused: bool) -> bool:
    global _spawn_paused
    with _spawn_pause_lock:
        _spawn_paused = bool(paused)
        return _spawn_paused
```

全局暂停标志阻止**新的**委派调用，但不中断正在运行的子代理。当 TUI 检测到失控的生成树时，操作员可以冻结新的 fan-out，同时让已有子代理自然完成。

### 6.2 活跃子代理注册表

```python
_active_subagents: Dict[str, Dict] = {}

# 每条记录包含：
{
    "subagent_id": "sa-0-a3f8c2d1",
    "parent_id": None,
    "depth": 0,
    "goal": "分析安全漏洞",
    "model": "gpt-4o",
    "started_at": 1717000000.0,
    "status": "running",
    "tool_count": 5,
    "agent": <AIAgent>,         # 仅进程内可见，TUI 快照会移除
}
```

注册表在 `_run_single_child` 的 `try/finally` 中维护——子代理启动时注册，完成（或异常）时注销。TUI 快照通过 `list_active_subagents()` 获取，自动移除不可序列化的 `agent` 引用。

### 6.3 中断传播

```python
def interrupt_subagent(subagent_id: str) -> bool:
    with _active_subagents_lock:
        record = _active_subagents.get(subagent_id)
    agent = record.get("agent")
    agent.interrupt(f"Interrupted via TUI ({subagent_id})")
```

中断通过 `AIAgent.interrupt()` 实现，设置 `_interrupt_requested` 标志，在子代理的下一次迭代边界（API 调用之间）生效。Python 无法硬 kill 线程，所以这是最安全的停止方式。中断会递归传播到孙代理。

### 6.4 输出尾部提取

`_extract_output_tail()` 从子代理的对话消息中提取最后 N 个工具调用结果，用于 TUI 的 "Output" 面板。每个条目包含 `{tool, preview, is_error}`，预览截断到 8000 字符，条目数上限 12。`_looks_like_error_output()` 使用保守启发式判断错误输出——仅在 JSON 包含 `error` 键、`status` 为 `error/failed/timeout`，或首行以 `error:/traceback/exception:` 开头时标记。

## 七、子代理上下文隔离的完整图景

```
+-----------------------------------------------------+
|                   父代理 (AIAgent)                    |
|  +---------------+  +--------------+                |
|  | 对话历史       |  | 完整工具集    |                |
|  | MEMORY.md     |  | delegate_task |                |
|  | clarify       |  | send_message  |                |
|  +-------+-------+  +------+-------+                |
|          |                 |                         |
|          |  delegate_task()|                         |
|          v                 v                         |
|  +---------------------------------------------+    |
|  |           子代理 (新 AIAgent 实例)            |    |
|  |  +------------------+  +-----------------+  |    |
|  |  | 全新对话历史      |  | 受限工具集       |  |    |
|  |  | (仅 goal 消息)   |  | (terminal, file, |  |    |
|  |  |                  |  |  web, ...)       |  |    |
|  |  +------------------+  +-----------------+  |    |
|  |  +------------------+  +-----------------+  |    |
|  |  | 聚焦系统提示词    |  | 独立 task_id    |  |    |
|  |  | (goal+context)   |  | 独立终端会话     |  |    |
|  |  +------------------+  +-----------------+  |    |
|  |  +------------------+  +-----------------+  |    |
|  |  | skip_memory=True |  | skip_context_   |  |    |
|  |  | clarify_cb=None  |  |  files=True     |  |    |
|  |  +------------------+  +-----------------+  |    |
|  +---------------------------------------------+    |
|          |                 |                         |
|          |  返回摘要结果    |                         |
|          v                 v                         |
|  +---------------------------------------------+    |

|  +---------------------------------------------+    |

```

系统提示词的构建逻辑体现了"最小必要信息"原则：

```python
def _build_child_system_prompt(goal, context, *, workspace_path, role, max_spawn_depth, child_depth):
    parts = [
        "You are a focused subagent working on a specific delegated task.",
        f"YOUR TASK:\n{goal}",
    ]
    if context: parts.append(f"\nCONTEXT:\n{context}")
    if workspace_path: parts.append(f"\nWORKSPACE PATH:\n{workspace_path}")
    if role == "orchestrator":
        # 追加委派指导、深度说明、何时/何时不委派
    return "\n".join(parts)
```

工作区路径通过 `_resolve_workspace_hint()` 从多个候选来源（`TERMINAL_CWD`、`_subdirectory_hints.working_dir`、`terminal_cwd`、`cwd`）中选择第一个有效的绝对路径，防止子代理猜测 `/workspace/...` 等容器路径。

## 八、心跳与卡死检测

子代理运行期间，父代理的 `_last_activity_ts` 冻结（因为父代理阻塞在 `delegate_task` 调用上）。如果没有心跳机制，网关会在超时后杀死整个代理。

`_heartbeat_loop()` 在独立守护线程中每 30 秒执行一次，调用 `parent_agent._touch_activity()` 保持网关活性。同时实现卡死检测：

```python
_HEARTBEAT_STALE_CYCLES_IDLE = 15     # 空闲：15 x 30s = 450s -> 视为卡死
_HEARTBEAT_STALE_CYCLES_IN_TOOL = 40  # 工具内：40 x 30s = 1200s -> 视为卡死
```

两种阈值的设计考虑：空闲（无 `current_tool`）时子代理可能在等待 API 响应，较短阈值确保真正卡住的子代理不会永远掩盖网关超时；工具内（`current_tool` 已设置）时子代理可能在执行合法的长耗时操作（终端命令、Web 抓取），使用更高阈值避免误判。

卡死后心跳线程停止触碰父代理，让网关超时自然触发，而不是主动中断——这是一个"消极发现"模式，而非"积极干预"。

## 九、配置键一览

所有委派相关配置位于 `config.yaml` 的 `delegation:` 键下：

| 配置键 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `max_concurrent_children` | int | 3 | 批量模式最大并发子代理数，最小值 1，超 10 会警告成本线性增长 |
| `max_spawn_depth` | int | 1 | 委派深度上限，范围 [1, 3]，默认扁平结构 |
| `child_timeout_seconds` | float | 600 | 单个子代理超时时间（秒），最小 30s |
| `orchestrator_enabled` | bool | true | Orchestrator 角色全局开关，false 时强制降级为 leaf |
| `subagent_auto_approve` | bool | false | 子代理危险命令自动审批，false=自动拒绝，true=YOLO 自动批准 |
| `inherit_mcp_toolsets` | bool | true | 子代理是否继承父代理的 MCP 工具集 |
| `max_iterations` | int | 50 | 每个子代理的迭代预算上限（独立于父代理） |

配置优先级：`config.yaml` > 环境变量（如 `DELEGATION_MAX_CONCURRENT_CHILDREN`）> 代码默认值。每个配置读取函数都遵循 `_load_config()` 路径，保持一致的优先级链。

## 十、设计启示

Hermes 的子代理委派系统展示了几条值得借鉴的设计原则：

1. **能力边界是安全边界**：`DELEGATE_BLOCKED_TOOLS` 不仅是功能限制，更是防止子代理产生不可控副作用的硬约束。每个屏蔽背后都有明确的安全动机。

2. **深度限制 + 角色降级**：双重防护——深度检查在入口处拒绝超出限制的委派，角色降级在构建时静默回退。两者配合确保即使配置错误也不会导致无限递归。

3. **线程安全需要显式设计**：`threading.local()` 不跨线程继承是 Python 的基本事实，但在 ThreadPoolExecutor 场景下极易被忽视。`initializer` 回调安装是简洁而正确的解决方案。

4. **消极发现优于积极干预**：心跳卡死检测不主动 kill 子代理，而是停止触碰父代理让网关超时自然触发。这种"消极发现"模式比"积极干预"更安全，因为它不会在子代理可能持有资源（文件锁、网络连接）时强制中断。

5. **全局可观测性**：`_active_subagents` 注册表和 `_spawn_paused` 标志让 TUI 和网关 RPC 能够实时监控和控制子代理树，将"黑盒执行"变为"可观测执行"。
