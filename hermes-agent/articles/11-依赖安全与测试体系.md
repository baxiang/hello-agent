## 引言：当你的 pip install 变成了攻击面

2026 年是 AI Agent 供应链安全的分水岭。3 月，广泛使用的 litellm 1.82.7/1.82.8 版本被发现包含凭证窃取器——通过 `.pth` 文件的 auto-exec 机制，在任何 Python 启动时自动执行，窃取 API Key、SSH 密钥和云凭证。5 月，Mini Shai-Hulud 蠕虫击中 PyPI 上的 mistralai 包，恶意版本 2.4.6 被推送后，包括 mistralai 在内的全部版本被 PyPI 隔离。

Hermes Agent 作为拥有 17 万+ star、近万次 commit 的生产级项目，这两次攻击不是遥远的新闻——litellm 正是 Hermes Agent 的硬依赖，攻击直接导致所有全新安装失败。

这套事件塑造了 Hermes Agent 当前的依赖安全体系。它不是一次性的"锁一下版本"，而是一套从 pyproject.toml 到 CI 审计的完整防线。

## 第一部分：依赖安全策略

### 1.1 两张表：从攻击事件到安全策略

Hermes Agent v0.15.1 的依赖安全策略可以概括为两张表——一张是规则表，一张是攻击历史如何塑造每条规则的对照表。

#### 1.1.1 litellm 凭证窃取攻击（2026 年 3 月）

**攻击路径**：litellm 1.82.7/1.82.8 在发布包中嵌入 `.pth` 文件，利用 Python 的 site-packages 自动执行机制，在任何 `import` 语句触发前执行 payload。Payload 扫描 `~/.ssh/`、`~/.aws/credentials`、`~/.config/gcloud/` 等路径，将凭证外发到攻击者控制的服务器。

PyPI 的反应是隔离整个 litellm 包——不仅撤下恶意版本，连历史正常版本也一并不可解析。对 Hermes Agent 的影响是即时的：**所有全新 `pip install` 失败**，因为 litellm 是 `pyproject.toml` 中的硬依赖。

**Hermes 的响应**（PR #2796）：
- 从 `pyproject.toml` 的 `dependencies` 列表中移除 `litellm`、`typer`、`platformdirs`——这些是 mini-swe-agent 子模块的依赖，被冗余声明在主项目中
- 修复 `install.sh` 中的日志错误（安装失败时仍打印 "installed"）
- 随后在一周内彻底移除 mini-swe-agent 子模块（PR #2804），将 Docker/Modal 终端后端实现内联到 Hermes 自身代码中

```python
# PR #2804 的核心变化：不再依赖外部子模块
# 旧：from mini_sweagent.environments import DockerEnvironment
# 新：直接在 environments/ 中实现 Docker 后端
# terminal_tool.py 不再需要 sys.path 黑魔法
```

**教训**：任何第三方包的任意版本都可能在一夜之间变得不可解析。唯一能阻止这种攻击影响你的用户的，是在攻击发生前就已经完成的架构解耦——将"可选功能"与"核心依赖"彻底分离。

#### 1.1.2 Mini Shai-Hulud 蠕虫（2026 年 5 月）

**攻击路径**：恶意版本 `mistralai==2.4.6` 被推送到 PyPI。与 litellm 不同，这次攻击针对的是范围版本声明——如果项目使用 `mistralai>=2.3.0,<3`，那么在 PyPI 隔离前的那几小时内拉取依赖的所有新安装，都会自动获取恶意版本。

**Hermes 的响应**（2026-05-12 的架构决策）：
- **核心依赖全部改为精确锁定** `==X.Y.Z`，不再使用范围版本
- 从 `[all]` extra 中移除所有可通过 lazy-install 加载的后端（anthropic, exa, firecrawl, fal, edge-tts, modal, daytona, messaging 全家桶, honcho, voice 等）
- `mistralai` extra 从 pyproject.toml 中删除并附带完整的恢复检查清单

```toml
# pyproject.toml 中 mistralai 的墓碑注释
# mistral: extra REMOVED 2026-05-12 — `mistralai` PyPI project quarantined
# after malicious 2.4.6 release (Mini Shai-Hulud worm). Every version of
# `mistralai` returns 404 on PyPI right now, so any pin we'd write is
# unresolvable, which breaks `uv lock --check` in CI.
#
# To restore once PyPI un-quarantines:
#   1. Verify the new release is clean (read the changelog, check Socket
#      advisory page, confirm no malicious code review findings).
#   2. Add back: mistral = ["mistralai==<verified-version>"]
#   3. Re-enable Mistral in:
#        - tools/lazy_deps.py (LAZY_DEPS["tts.mistral"], LAZY_DEPS["stt.mistral"])
#        - hermes_cli/tools_config.py (un-hide from provider picker)
#        - hermes_cli/web_server.py (re-add to dashboard STT options)
#        - tools/transcription_tools.py / tools/tts_tool.py (drop disabled stubs)
#   4. Run `uv lock` to regenerate transitives.
#   5. Optionally re-add to [all] only after a few days of clean operation.
```

这不是"删除一行依赖"——这是一份完整的灾难恢复运行手册，确保未来任何贡献者都能按步骤恢复而不遗漏。

### 1.2 精确锁定：为什么 `>=` 是危险的

Hermes Agent v0.15.1 的核心依赖全部使用 `==` 精确锁定：

```toml
dependencies = [
  "openai==2.24.0",
  "python-dotenv==1.2.2",
  "fire==0.7.1",
  "httpx[socks]==0.28.1",
  "rich==14.3.3",
  "tenacity==9.1.4",
  "pyyaml==6.0.3",
  "ruamel.yaml==0.18.17",
  "requests==2.33.0",  # CVE-2026-25645
  "jinja2==3.1.6",
  "pydantic==2.13.4",
  "prompt_toolkit==3.0.52",
  "croniter==6.0.0",
  "PyJWT[crypto]==2.12.1",  # CVE-2026-32597
  "psutil==7.2.2",
]
```

设计理念在 pyproject.toml 的顶部注释中说得非常清楚：

> **Core — every direct dep is exact-pinned to `==X.Y.Z` (no ranges).**
> Rationale: ranges allow PyPI to ship a fresh version of a transitive at
> any time without a code review on our side. Exact pins mean the only way
> a new package version reaches a user is via an intentional update on our
> end (bump the pin in this file, regenerate uv.lock).

这个策略有三层含义：

| 层 | 描述 |
|---|---|
| **防止恶意包自动拉取** | 范围版本 `>=x,<y` 会在恶意版本推送后自动选中它。精确锁定则意味着除非有人刻意改版本号，否则不会变 |
| **强制变更审计** | 每次版本升级都需要（1）修改 pyproject.toml 中的版本号，（2）运行 `uv lock` 重新生成 uv.lock。这两步都经过代码审查 |
| **可重现构建** | `uv.lock` 包含 sha256 哈希，精确锁定所有传递依赖。同一套锁文件在任何机器上解析出的依赖树完全相同 |

可选依赖同样遵循此规则——它们通过 lazy-install 加载，但 lazy_deps.py 中声明的版本同样是精确的 `==`：

```python
# tools/lazy_deps.py 中的精确版本锁定
LAZY_DEPS: dict[str, tuple[str, ...]] = {
    "provider.anthropic": ("anthropic==0.87.0",),
    "search.exa": ("exa-py==2.10.2",),
    "tts.edge": ("edge-tts==7.2.7",),
    "tts.elevenlabs": ("elevenlabs==1.59.0",),
    # ... 所有后端均精确锁定
}
```

### 1.3 范围版本 vs 精确版本：政策表

完整的依赖处理策略：

| 来源 | 处理方式 | 示例 |
|---|---|---|
| PyPI 核心依赖 | `==X.Y.Z` 精确锁定 | `"openai==2.24.0"` |
| PyPI 非核心（可选 extras） | `==X.Y.Z` 精确锁定 | `"anthropic==0.86.0"`, `"firecrawl-py==4.17.0"` |
| Git URL 依赖 | Commit SHA | `git+https://...@<40-char-sha>` |
| GitHub Actions | Commit SHA + 注释别名 | `uses: actions/checkout@<sha> # v4` |
| CI-only pip | `==X.Y.Z` 精确锁定 | `"pyyaml==6.0.2"` |

注意：**Hermes Agent 不再使用任何范围版本**。即使是 `httpx>=0.28.1,<1` 这样的保守范围也已被精确锁定替代。pyproject.toml 的注释明确指出：

> When updating: bump the version below AND regenerate uv.lock with
> `uv lock` so the transitive resolution stays consistent. Don't
> introduce ranges back without a written justification.

### 1.4 依赖范围的"爆炸半径"控制

在 Mini Shai-Hulud 攻击后，Hermes 做出了一个关键的架构决策：**核心依赖列表必须尽可能小**。

```
依赖分层架构：

┌──────────────────────────────────────────┐
│  Core dependencies (pyproject.toml)       │
│  每次 hermes 会话都需要的包               │
│  openai, httpx, rich, pydantic, ...       │
│  ← 最小的爆炸半径                         │
├──────────────────────────────────────────┤
│  Extras (pyproject.toml [optional])       │
│  打包器(Nix/AUR/Homebrew)需要的包         │
│  google, youtube, web, ...                │
│  ← 只在用户显式选择时安装                 │
├──────────────────────────────────────────┤
│  LAZY_DEPS (tools/lazy_deps.py)           │
│  提供者/后端特定的包                       │
│  anthropic, firecrawl, fal, edge-tts, ... │
│  ← 首次使用时按需安装，独立隔离            │
└──────────────────────────────────────────┘
```

一条严格的规则：**只有每个 hermes 会话都使用的包才属于核心依赖**。所有提供者特定的包（anthropic, firecrawl-py, exa-py, fal-client, edge-tts, parallel-web）都属于 extras 或 LAZY_DEPS，在用户选择对应后端时才被加载。

```python
# pyproject.toml 中的范围规则注释
# Scope rule: only packages used by EVERY hermes session belong here.
# Anything that's provider-specific (`anthropic`, `firecrawl-py`,
# `exa-py`, `fal-client`, `edge-tts`, `parallel-web`) belongs in an
# extra and gets lazy-installed via `tools/lazy_deps.py` when the
# user picks that backend. Smaller `dependencies` = smaller blast
# radius for the next supply-chain attack.
```

### 1.5 懒加载依赖系统：tools/lazy_deps.py

核心技术实现文件是 `tools/lazy_deps.py`。它解决了以下问题：

1. **脆弱性**：一个 extra 的传递依赖被 PyPI 隔离时，`[all]` 整体解析失败，导致无关的 10+ 个 extra 全部丢失
2. **膨胀**：只使用一个提供者的用户也会拉取数百个永远不用的包
3. **安全性**：任何不在 LAZY_DEPS 白名单中的包都无法通过懒加载路径安装

```python
# tools/lazy_deps.py 核心 API 设计
def ensure(feature: str, *, prompt: bool = True) -> None:
    """确保 feature 的所有包已安装且版本匹配。
    
    缺失时尝试在活动 venv 中安装。
    如果用户禁用了懒加载或安装失败，抛出 FeatureUnavailable。
    """
```

使用模式——在平台适配器中的典型调用：

```python
def check_slack_requirements() -> bool:
    if SLACK_AVAILABLE:
        return True
    def _import():
        from slack_bolt.async_app import AsyncApp
        from slack_sdk.web.async_client import AsyncWebClient
        return {"AsyncApp": AsyncApp, "AsyncWebClient": AsyncWebClient,
                "SLACK_AVAILABLE": True}
    return ensure_and_bind("platform.slack", _import, globals(), prompt=False)
```

**安全模型**包含五层防护：

| 层级 | 措施 |
|---|---|
| **Venv 隔离** | 只安装在 `sys.executable` 所在的 venv 中，绝不触碰系统 Python |
| **包名白名单** | 只接受 `LAZY_DEPS` 中的 spec，拼写错误不会导致安装任意包 |
| **Spec 安全校验** | 拒绝含 URL、文件路径、shell 元字符的 spec（`_SAFE_SPEC` 正则） |
| **用户可退出** | 设置 `security.allow_lazy_installs: false` 禁用运行时安装 |
| **离线检测** | 安装失败时通过 `FeatureUnavailable` 暴露完整错误信息，不静默重试 |

### 1.6 SECURITY.md：信任模型与安全边界

Hermes Agent 的 `SECURITY.md` 不是摆设。它定义了一套清晰的安全态势，核心是一个明确的声明：

> **对抗对抗性 LLM 的唯一安全边界是操作系统。**
> 审批门禁、输出脱敏、模式扫描器——这些是启发式工具，不是边界。

SECURITY.md 定义了三个关键概念：

1. **信任信封**：操作者运行 Hermes Agent 时隐式授予其访问的资源集合
2. **OS 级别隔离**：终端后端隔离（容器/远程/云沙箱）vs 全进程包装（Docker/NVIDIA OpenShell）
3. **外部表面的统一授权规则**：每个网络暴露的适配器都需要调用者白名单

对于依赖安全而言，最重要的段落是 §2.5 "Plugin Trust Model"——插件加载进 Agent 进程并获得完整权限。边界是操作者在安装前的审查。

## 第二部分：测试体系

### 2.1 子进程隔离：每条测试文件一个全新的 Python 解释器

Hermes Agent 的测试体量巨大——约 **850 个测试文件，17,000+ 个测试用例**。在这个规模下，测试隔离不是可选项，而是生存必需。

**设计演进**：

```
v0.2 〜 v0.7:  module-level state reset（手动清理）
  ↓ 问题：漏清理导致跨文件状态泄漏，CI 不稳定
v0.8 〜 v0.9:  pytest-xdist（持久 worker 进程）
  ↓ 问题：xdist 的 worker 跨文件积累状态，这正是要解决的问题
v0.10+    :  每个文件一个独立 Python 子进程
  ↓ 当前方案
```

**为什么不按测试隔离（per-test）？** 简单算笔账：

```
Per-test spawn: 250ms × 17,000 tests = 4,250s ≈ 71min（只有子进程启动开销）
Per-file spawn: 250ms × 850 files  = 212s  ≈ 3.5min
```

Per-file 方案在预算内提供了唯一真正有效的隔离——跨文件模块级状态泄漏被彻底消灭。至于文件内部的测试顺序，那是测试作者的责任。

核心实现是 `scripts/run_tests_parallel.py`，一个 ~600 行的最小化并行测试运行器。关键设计：

```python
# 核心执行函数：每个文件一个子进程
def _run_one_file(file, pytest_args, repo_root, file_timeout):
    cmd = [sys.executable, "-m", "pytest", str(file), *pytest_args]
    proc = subprocess.Popen(
        cmd, stdout=subprocess.PIPE, stderr=subprocess.STDOUT,
        text=True,
        start_new_session=True,  # POSIX: 子进程在自己的进程组中
    )
    # 捕获 PGID，防止子进程被收割后孙进程泄漏
    pgid = os.getpgid(proc.pid) if sys.platform != "win32" else None
    
    try:
        output, _ = proc.communicate(timeout=file_timeout)
    except subprocess.TimeoutExpired:
        _kill_tree(proc, pgid=pgid)  # 杀掉整个进程树
```

**进程树清理**是最容易出问题也最重要的部分。

```python
def _kill_tree(proc, pgid=None):
    if sys.platform == "win32":
        subprocess.run(["taskkill", "/F", "/T", "/PID", str(proc.pid)], ...)
    else:
        os.killpg(pgid, signal.SIGKILL)  # 原子地杀死整个进程组
```

这里有一个非常微妙的点：**PGID 必须在 `Popen` 返回后立即捕获**。一旦子进程退出（竞技条件），`os.getpgid(proc.pid)` 就会抛出 `ProcessLookupError`——而此时孙进程（uvicorn 服务器、asyncio 运行时等）可能仍然存活，被 reparent 到 PID 1 并泄漏。

同样的逻辑，即使在正常退出路径（pytest 自行退出）下也会执行 `_kill_tree`，因为"行为良好的子进程会清理自己的孙子"这个假设不总是成立。

### 2.2 并行执行与 P50 性能

`run_tests_parallel.py` 使用线程池 + 信号量进行并行控制：

```python
with ThreadPoolExecutor(max_workers=args.jobs) as pool:
    for file in files:
        fut = pool.submit(_run_one_file, file, ...)
        fut.add_done_callback(lambda f: _on_done(...))
```

默认并行度是 **CPU 核数 × 2**（可通过 `HERMES_TEST_WORKERS` 覆写）。

性能数据（per-file 子进程时间分布）：

- **P50**: ~0.5-1.0s / 文件
- **P90**: ~3-5s
- **P95**: ~8-12s
- **文件超时**: 600s（pytest-timeout 在每个子进程内部还有 30s 的 per-test 上限）

对于 CI，提供了 `--slice I/N` 功能——使用 LPT（最长处理时间优先）算法按文件预估耗时分布到 N 个并行 job 中，确保每个 job 的 wall time 大致均衡。

### 2.3 测试包装器：CI 对等保证

`scripts/run_tests.sh` 是规范的测试入口。它通过环境净化确保本地运行与 CI 完全一致：

```bash
exec env -i \
  PATH="$PATH" \
  HOME="$HOME" \
  TZ=UTC \
  LANG=C.UTF-8 \
  LC_ALL=C.UTF-8 \
  PYTHONHASHSEED=0 \
  "$PYTHON" "$SCRIPT_DIR/run_tests_parallel.py" "$@"
```

关键环境净化项：

| 设置 | 目的 |
|---|---|
| `env -i` | 从空环境启动，只显式开放需要的变量 |
| `TZ=UTC` | 防止时区相关测试在本地（如 Asia/Shanghai）通过但在 UTC CI 中失败 |
| `LANG=C.UTF-8` | 防止 locale 敏感的字符串排序/比较在不同环境中行为不同 |
| `PYTHONHASHSEED=0` | 确定性哈希，防止 dict/set 迭代顺序在不同运行中变化 |
| 所有 `*_API_KEY/*_TOKEN/*_SECRET` 被 unset | 防止开发者的本地密钥泄漏到测试环境 |

`conftest.py` 进一步在 Python 层面强化了这些隔离。以下是 `_hermetic_environment` autouse fixture 的核心逻辑：

```python
@pytest.fixture(autouse=True)
def _hermetic_environment(tmp_path, monkeypatch):
    # 1. 清除所有凭证形状的环境变量
    for name in list(os.environ.keys()):
        if _looks_like_credential(name):
            monkeypatch.delenv(name, raising=False)
    
    # 2. 清除行为性 HERMES_* 变量
    for name in _HERMES_BEHAVIORAL_VARS:
        monkeypatch.delenv(name, raising=False)
    
    # 3. 将 HERMES_HOME 重定向到临时目录
    fake_hermes_home = tmp_path / "hermes_test"
    fake_hermes_home.mkdir()
    monkeypatch.setenv("HERMES_HOME", str(fake_hermes_home))
    
    # 4. 确定性时区/语言/哈希
    monkeypatch.setenv("TZ", "UTC")
    monkeypatch.setenv("LANG", "C.UTF-8")
```

### 2.4 凭证过滤器的实现

`conftest.py` 维护了一个详细的凭证识别系统。它通过两层规则识别需要清除的环境变量：

**第一层：后缀匹配**。任何以这些后缀结尾的变量都被识别为凭证：

```python
_CREDENTIAL_SUFFIXES = (
    "_API_KEY", "_TOKEN", "_SECRET", "_PASSWORD", "_CREDENTIALS",
    "_ACCESS_KEY", "_SECRET_ACCESS_KEY", "_PRIVATE_KEY", "_OAUTH_TOKEN",
    "_WEBHOOK_SECRET", "_ENCRYPT_KEY", "_APP_SECRET",
    "_CLIENT_SECRET", "_CORP_SECRET", "_AES_KEY",
)
```

**第二层：显式名称集合**。对不符合后缀模式的凭证进行逐个命名（100+ 个条目），包括：

```
OPENAI_API_KEY, OPENROUTER_API_KEY, TELEGRAM_BOT_TOKEN,
DISCORD_BOT_TOKEN, SLACK_BOT_TOKEN, ANTHROPIC_TOKEN, FAL_KEY,
GH_TOKEN, GITHUB_TOKEN, MODAL_TOKEN_ID, MODAL_TOKEN_SECRET,
WECOM_CALLBACK_TOKEN, WECOM_CALLBACK_ENCODING_AES_KEY, ...
```

此外，一个单独的行为性变量集合 `_HERMES_BEHAVIORAL_VARS`（~120 个条目）涵盖了所有可能改变测试语义的 `HERMES_*` 和网关行为变量——包括会话标识、平台设置、kanban 路径、仪表板 OAuth 配置等。

### 2.5 live-system guard：防止测试杀死真实网关

`conftest.py` 中还有一个防御性的 fixture `_live_system_guard`——它的存在是因为一次真实事故。PR #23285 的取证分析发现，在 3 天内发生了 5+ 次事件：某个测试忘记 mock `os.kill`，结果真实调用了开发者的生产 Hermes Gateway 进程并发送了 SIGTERM。

```python
@pytest.fixture(autouse=True)
def _live_system_guard(request, monkeypatch):
    test_pid = os.getpid()
    
    def _guarded_kill(pid, sig):
        if _is_own_subtree(int(pid)):
            return real_kill(pid, sig)
        raise RuntimeError(
            f"tests/conftest.py live-system guard: blocked os.kill("
            f"{pid}, {sig}) — PID is outside the test process subtree."
        )
    
    monkeypatch.setattr(os, "kill", _guarded_kill)
```

这个 fixture 拦截了所有可能向外部进程发送信号的原语：
- `os.kill` / `os.killpg`（拒绝测试进程子树外的 PID）
- `subprocess.run` / `Popen` / `call` / `check_call` / `check_output`（阻止包含 `systemctl restart hermes-gateway` 等模式的命令）
- `pkill` / `killall` / `taskkill` 调用
- `asyncio.create_subprocess_exec` / `create_subprocess_shell`

### 2.6 反变更检测测试规则

Hermes Agent 的测试作者需要遵循一条明确的规则——**区分"你期望不变的东西"和"你知道会变的东西"**。

| 不要写 | 要写 |
|---|---|
| 快照测试（verify that specific model name exists in catalog） | 不变量测试（verify every model in catalog has a context-length entry） |
| `assert catalog["gpt-4o"]["context_length"] == 128000` | `assert all("context_length" in m for m in catalog.values())` |
| 硬编码特定 API 返回值 | 验证返回值的结构约束 |

**快照测试（change-detector tests）** 是测试反模式——它们在你期望变化的数据发生变化时断裂，但断裂本身不告诉你任何有用的信息。当你更新模型目录，把所有 `gpt-4o` 改成 `gpt-5`时，快照测试会因完全不相关的原因失败。

**不变量测试（invariant tests）** 测试的是数据之间的关系契约。比如："每个模型定义都包含 context_length 字段"——这是一个关于数据结构的真理，无论模型名称如何变化都为真。这种测试在数据更新时不会断裂，但当有人提了一个缺少 context_length 字段的新模型 PR 时会提供有价值的失败信号。

### 2.7 timeout 的双层防护

每个测试受到两层超时保护：

```
外层的 run_tests_parallel.py
  │
  │  file_timeout = 600s (默认) / HERMES_TEST_FILE_TIMEOUT
  │  如果整个文件的 pytest 在 10 分钟内未退出，杀掉进程树
  │
  ▼
内层的 pytest 子进程
  │
  │  pytest-timeout = 30s (pyproject.toml [tool.pytest.ini_options])
  │  如果单个测试在 30 秒内未完成，SIGALRM 终止
  │
  ▼
  测试代码
```

```toml
# pyproject.toml 中的 pytest-timeout 配置
[tool.pytest.ini_options]
addopts = "-m 'not integration' --timeout=30 --timeout-method=signal"
```

外层超时的作用域是"一个文件"，用于处理整个文件挂起、无限循环或死锁的情况。内层超时的作用域是"一个测试函数"，由 pytest-timeout 在每个子进程内部强制执行。双层防护确保即使 pytest 自己的超时机制失效（例如被 C 扩展阻塞），外层也能在 10 分钟后介入。

### 2.8 CI 切片与时长缓存

`test_durations.json` 记录每个测试文件上次运行的 wall time：

```python
def _save_durations(file_times, repo_root):
    data = _load_durations(repo_root)  # 合并已有数据
    for f, t in file_times:
        key = _format_file(f, repo_root)
        data[key] = round(t, 3)
    path = repo_root / _DURATIONS_FILE
    path.write_text(json.dumps(data, indent=2, sort_keys=True) + "\n")
```

在 CI 中使用 `--slice 1/4` 将测试文件按 LPT 算法分布到 4 个并行 job：

```python
def _slice_files(files, slice_index, slice_count, durations, repo_root):
    # LPT (Longest Processing Time first) 算法
    file_durs.sort(key=lambda x: x[1], reverse=True)
    bucket_totals = [0.0] * slice_count
    
    for f, dur in file_durs:
        min_idx = min(range(slice_count), key=lambda i: bucket_totals[i])
        bucket_files[min_idx].append(f)
        bucket_totals[min_idx] += dur
    
    return bucket_files[slice_index - 1]
```

没有缓存的新文件被赋予 2.0s 的默认预估。LPT 算法保证每个 slice 的预估总时间尽可能均衡，让并行 CI job 几乎同时完成。

## 结语

Hermes Agent 的依赖安全策略和测试体系不是一次性设计的结果，而是两次真实供应链攻击和数千次 CI 故障的后验修正。核心原则有三条：

1. **精确锁定就是安全**：`==X.Y.Z` 不是保守，是把"新版本何时到达用户"的控制权从 PyPI 收回项目
2. **最小核心 = 最小爆炸半径**：不是每个功能都需要在 `pip install` 时一起拉下来；lazy-install 把可选依赖的攻击面独立隔离
3. **隔离是可测试性的基础**：Per-file 子进程隔离的 250ms 开销，换来的是跨文件状态泄漏这个故障来源的彻底消灭

在 17,000 个测试和 2965 个锁定传递依赖的规模上，这些原则不是锦上添花——它们是唯一的可行方式。
