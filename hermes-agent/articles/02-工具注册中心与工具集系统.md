# 工具注册中心与工具集系统：Hermes Agent 的能力编排引擎

> 源码版本: v0.15.1 | 核心文件: `tools/registry.py`, `toolsets.py`, `agent/tool_guardrails.py`

## 引言

一个 Agent 的能力边界，不取决于它拥有多少工具，而取决于它如何**发现**、**组织**和**管控**这些工具。Hermes Agent 在 v0.15.1 中构建了一套三层架构——零依赖单例注册中心、声明式工具集组合、以及基于签名的工具调用护栏。本文深入剖析其设计哲学与实现细节。

## 一、注册中心核心设计 (tools/registry.py)

### 1.1 AST 扫描发现：零导入成本的模块加载

Hermes 的工具发现机制并不依赖 `__all__`、装饰器或手动导入列表，而是采用 **AST 静态扫描**：

```python
def _module_registers_tools(module_path: Path) -> bool:
    source = module_path.read_text(encoding="utf-8")
    tree = ast.parse(source, filename=str(module_path))
    return any(_is_registry_register_call(stmt) for stmt in tree.body)
```

核心逻辑：`_is_registry_register_call()` 检查模块的**顶层语句**中是否存在 `registry.register(...)` 调用。只扫描 `tree.body`（模块顶层），忽略函数体内部的调用——这避免了将辅助模块误判为工具模块。

`discover_builtin_tools()` 扫描 `tools/` 目录下所有 `.py` 文件，只导入通过 AST 检查的模块：

```python
def discover_builtin_tools(tools_dir=None):
    module_names = [
        f"tools.{path.stem}"
        for path in sorted(tools_path.glob("*.py"))
        if path.name not in {"__init__.py", "registry.py", "mcp_tool.py"}
        and _module_registers_tools(path)   # AST 预过滤
    ]
    for mod_name in module_names:
        importlib.import_module(mod_name)    # 仅导入确认包含注册调用的模块
```

**设计收益**：避免导入不含工具注册的辅助模块（如 `registry.py` 自身、`mcp_tool.py`），减少启动时副作用和循环导入风险。

### 1.2 ToolEntry 数据类：`__slots__` 的极致内存优化

```python
class ToolEntry:
    __slots__ = (
        "name", "toolset", "schema", "handler", "check_fn",
        "requires_env", "is_async", "description", "emoji",
        "max_result_size_chars", "dynamic_schema_overrides",
    )
```

使用 `__slots__` 而非常规类字典，每个实例节省约 40% 内存（无 `__dict__` 开销），在注册 50+ 工具时差异显著。各字段职责：

| 字段 | 用途 |
|------|------|
| `name` | 工具唯一标识符 |
| `toolset` | 所属工具集（如 `"browser"`, `"mcp-xxx"`） |
| `schema` | OpenAI function-calling 格式的 JSON Schema |
| `handler` | 实际执行函数 |
| `check_fn` | 可用性检查函数（Docker/Modal/Playwright 探针） |
| `requires_env` | 所需环境变量列表 |
| `is_async` | 是否为异步处理器 |
| `max_result_size_chars` | 单工具结果截断阈值 |
| `dynamic_schema_overrides` | 运行时 Schema 覆盖的可调用对象 |

### 1.3 check_fn TTL 缓存：30 秒的可用性探测窗口

工具可用性检查（如 Docker 守护进程是否运行、Playwright 是否安装）属于**昂贵的外部状态探测**。Hermes 用 30 秒 TTL 缓存规避重复探测：

```python
_CHECK_FN_TTL_SECONDS = 30.0
_check_fn_cache: Dict[Callable, tuple[float, bool]] = {}
_check_fn_cache_lock = threading.Lock()

def _check_fn_cached(fn: Callable) -> bool:
    now = time.monotonic()
    with _check_fn_cache_lock:
        cached = _check_fn_cache.get(fn)
        if cached is not None:
            ts, value = cached
            if now - ts < _CHECK_FN_TTL_SECONDS:
                return value        # 缓存命中
    try:
        value = bool(fn())
    except Exception:
        value = False               # 探测异常一律视为不可用
    with _check_fn_cache_lock:
        _check_fn_cache[fn] = (now, value)
    return value
```

**为什么是 30 秒**？外部状态（Docker 启停、`hermes tools enable` 命令修改环境变量）在人类时间尺度变化，30 秒保证配置变更在 1-2 轮对话内传播，同时避免每次 `get_definitions()` 都触发 Docker/Modal API 探测。

`invalidate_check_fn_cache()` 在 `hermes tools enable` 等配置变更后主动调用，实现即时失效。

### 1.4 线程安全快照与代际计数器

注册中心可能被多线程并发访问（CLI 主线程 + MCP 动态刷新线程），核心保护机制：

```
+-----------------------------------------------------+
|                  ToolRegistry                        |
|                                                      |
|  _lock = threading.RLock()                          |
|  _generation: int  (单调递增)                        |
|  _tools: Dict[str, ToolEntry]                       |
|  _toolset_checks: Dict[str, Callable]               |
|                                                      |
|  _snapshot_state() ---> (entries_copy, checks_copy) |
|       |  在 RLock 保护下拷贝                        |
|       |  返回后调用者持有不可变快照                    |
|       V                                              |
|  外部缓存可基于 _generation 做失效判断:               |
|    if cached_gen != registry._generation:            |
|        rebuild_cache()                               |
+-----------------------------------------------------+
```

- **`_snapshot_state()`**：在 RLock 保护下返回 `(list(entries), dict(checks))`，调用者持有一个**语义上不可变**的快照，无需持续持锁
- **`_generation`**：每次 `register()`/`deregister()`/`register_toolset_alias()` 递增。外部模块（如 `model_tools.get_tool_definitions`）用它做缓存键——如果 generation 未变，缓存有效；一旦递增，重建缓存

### 1.5 影子覆盖保护：防止工具名冲突

```python
def register(self, name, toolset, ..., override=False):
    existing = self._tools.get(name)
    if existing and existing.toolset != toolset:
        both_mcp = (
            existing.toolset.startswith("mcp-")
            and toolset.startswith("mcp-")
        )
        if both_mcp:
            pass                    # MCP->MCP 覆盖合法（服务器刷新）
        elif override:
            pass                    # 显式 opt-in 覆盖（插件替换内置工具）
        else:
            logger.error("Tool registration REJECTED: ...")
            return                  # 拒绝：不同 toolset 同名工具
```

三级覆盖策略：

1. **MCP->MCP**：允许。两个 MCP 服务器提供同名工具是合法场景（服务器刷新、多服务器重叠）
2. **`override=True`**：允许。插件显式声明替换内置工具（如用 Chrome CDP 后端替换默认浏览器工具），INFO 级别日志留痕审计
3. **其他情况**：REJECTED。防止意外覆盖导致工具静默丢失

### 1.6 动态 Schema 覆盖

`dynamic_schema_overrides` 是一个零参数可调用对象，在 `get_definitions()` 时每次调用，返回值浅合并到基础 Schema 之上：

```python
# ToolEntry 初始化时
self.dynamic_schema_overrides = dynamic_schema_overrides

# get_definitions() 调用时
if entry.dynamic_schema_overrides is not None:
    overrides = entry.dynamic_schema_overrides()  # 每次实时计算
    if isinstance(overrides, dict):
        schema_with_name.update(overrides)        # 浅合并
```

典型用例：`delegate_task` 工具的 description 需反映当前 `delegation.max_concurrent_children` 和 `max_spawn_depth` 配置值，避免模型看到过时的限制参数。

### 1.7 tool_error() 与 tool_result() 序列化辅助

所有工具处理器必须返回 JSON 字符串。这两个辅助函数消除了跨工具文件数百次 `json.dumps({"error": msg}, ensure_ascii=False)` 的样板代码：

```python
def tool_error(message, **extra) -> str:
    result = {"error": str(message)}
    if extra:
        result.update(extra)
    return json.dumps(result, ensure_ascii=False)

def tool_result(data=None, **kwargs) -> str:
    if data is not None:
        return json.dumps(data, ensure_ascii=False)
    return json.dumps(kwargs, ensure_ascii=False)
```

### 2.3 递归组合与菱形依赖

工具集支持 `includes` 字段实现递归组合：

```python
"debugging": {
    "tools": ["terminal", "process"],
    "includes": ["web", "file"]    # 递归包含 web 和 file 工具集
},
"hermes-gateway": {
    "tools": [],
    "includes": ["hermes-telegram", "hermes-discord", "hermes-whatsapp", ...]
}
```

`resolve_toolset()` 用 `visited` 集合处理菱形依赖和环检测：

```python
def resolve_toolset(name, visited=None):
    if visited is None:
        visited = set()
    if name in {"all", "*"}:          # 特殊别名：所有工具集的并集
        return union_of_all_toolsets()
    if name in visited:               # 菱形依赖 / 环检测
        return []                     # 静默跳过
    visited.add(name)
    tools = set(toolset.get("tools", []))
    for included_name in toolset.get("includes", []):
        tools.update(resolve_toolset(included_name, visited))  # 共享 visited
    return sorted(tools)
```

**关键细节**：`visited` 在兄弟 include 间**共享**，确保菱形依赖只解析一次，且环检测不会对同一环多次警告。

### 2.4 hermes-* 自动生成

当 `resolve_toolset()` 遇到未定义的 `hermes-*` 名称时，自动查询 `platform_registry`：

```python
if name.startswith("hermes-"):
    platform_name = name[len("hermes-"):]
    if platform_registry.is_registered(platform_name):
        plugin_tools = set(_HERMES_CORE_TOOLS)
        plugin_tools.update(registry tools for platform_name)
        return list(plugin_tools)
```

这意味着新增一个平台只需在 `platform_registry` 注册，无需手动在 `TOOLSETS` 字典中添加条目。

## 三、工具护栏 (agent/tool_guardrails.py)

### 3.1 工具分类：幂等 vs 变异

```python
IDEMPOTENT_TOOL_NAMES = frozenset({
    "read_file", "search_files", "web_search", "web_extract",
    "session_search", "browser_snapshot", "browser_console", ...
})

MUTATING_TOOL_NAMES = frozenset({
    "terminal", "execute_code", "write_file", "patch",
    "browser_click", "browser_type", "send_message", "delegate_task", ...
})
```

分类决定了不同的循环检测策略：
- **幂等工具重复**：同参数同结果 -> "无进展"检测
- **变异工具重复**：同参数反复失败 -> "精确失败"检测

### 3.2 ToolCallSignature：SHA-256 签名的不可逆指纹

```python
@dataclass(frozen=True)
class ToolCallSignature:
    tool_name: str
    args_hash: str                    # SHA-256(canonical_json(args))

    @classmethod
    def from_call(cls, tool_name, args):
        canonical = canonical_tool_args(args or {})
        return cls(tool_name=tool_name, args_hash=_sha256(canonical))
```

`canonical_tool_args()` 将参数排序后紧凑序列化（`sort_keys=True, separators=(",",":")`），确保语义相同的参数生成相同哈希。SHA-256 不可逆——护栏系统可以检测重复调用，但无法还原原始参数值。

### 3.3 四级决策模型

```
+-----------------------------------------------------+
|          ToolGuardrailDecision                       |
|                                                      |
|  allow --> 正常执行，无额外处理                      |
|  warn  --> 执行，但追加警告到 tool result           |
|  block --> 拒绝执行，返回合成错误                    |
|  halt  --> 拒绝执行 + 标记终止当前 turn             |
|                                                      |
|  allows_execution = action in {"allow", "warn"}     |
|  should_halt      = action in {"block", "halt"}     |
+-----------------------------------------------------+
```

### 3.4 ToolCallGuardrailConfig：渐进式阈值

```python
@dataclass(frozen=True)
class ToolCallGuardrailConfig:
    warnings_enabled: bool = True          # 警告默认开启
    hard_stop_enabled: bool = False        # 硬停止默认关闭（需显式 opt-in）
    exact_failure_warn_after: int = 2      # 同参数失败 2 次 -> warn
    exact_failure_block_after: int = 5     # 同参数失败 5 次 -> block
    same_tool_failure_warn_after: int = 3  # 同工具不同参数失败 3 次 -> warn
    same_tool_failure_halt_after: int = 8  # 同工具不同参数失败 8 次 -> halt
    no_progress_warn_after: int = 2        # 幂等工具同结果 2 次 -> warn
    no_progress_block_after: int = 5       # 幂等工具同结果 5 次 -> block
```

**设计哲学**：警告永远不阻止执行——交互式 CLI/TUI 优先获得温和提示；硬停止需要用户在 `config.yaml` 中显式启用，作为断路器保护无人值守场景。

### 3.5 检测流程

```
before_call(tool_name, args)
    |
    +-- 精确失败计数 >= block_after?  --> block (repeated_exact_failure_block)
    +-- 幂等工具无进展 >= block_after? --> block (idempotent_no_progress_block)
    +-- otherwise                     --> allow

after_call(tool_name, args, result, failed=?)
    |
    +-- failed?
    |   +-- 精确失败计数++
    |   +-- 同工具失败计数++
    |   +-- same_count >= halt_after?      --> halt (same_tool_failure_halt)
    |   +-- exact_count >= warn_after?     --> warn (repeated_exact_failure_warning)
    |   +-- same_count >= warn_after?      --> warn (same_tool_failure_warning)
    |
    +-- 成功
        +-- 非幂等工具: 清除计数器 --> allow
        +-- 幂等工具:
            +-- 结果哈希相同? 无进展计数++
            +-- no_progress >= warn_after?  --> warn (idempotent_no_progress_warning)
            +-- otherwise                  --> allow
```

## 四、注册与暴露的分离：一个关键的设计哲学

Hermes 的工具系统有一个贯穿始终的设计原则：**注册（Registration）和暴露（Exposure）是两个独立步骤**。

```
+------------+     +------------+     +------------+     +------------+
|   注册阶段  |     |   解析阶段  |     |   过滤阶段  |     |   护栏阶段  |
| registry.  |     | resolve_   |     | check_fn   |     | guardrail  |
| register() |     | toolset()  |     | TTL cache  |     | controller |
+------------+     +------------+     +------------+     +------------+
      |                  |                  |                  |
      v                  v                  v                  v
 ToolEntry          Set[str]          可用子集           决策结果
 (全量元数据)      (工具名集合)      (通过检查的工具)    (allow/warn/block/halt)
```

**为什么不能合并注册和暴露**？

1. **MCP 动态刷新**：MCP 服务器可能在运行时加入/离开，工具需要先注册再按需暴露。合并意味着每次 MCP 变更都要重建整个工具表
2. **跨平台复用**：同一个 `terminal` 工具在 CLI 和 webhook 场景下注册逻辑完全相同，但暴露策略截然不同（CLI 允许，webhook 禁止）。注册是**能力声明**，暴露是**权限控制**
3. **check_fn 延迟求值**：注册时并不知道 Docker 是否在运行，只有在 `get_definitions()` 时才探测。将可用性检查绑定到注册阶段会迫使启动时探测所有外部依赖
4. **插件安全**：插件可以自由注册工具（声明"我能做 X"），但工具是否被暴露给模型由 toolset 配置决定。这种分离防止了恶意插件通过注册直接将自身注入模型上下文

这种设计的代价是概念复杂度的增加——开发者需要理解从注册到暴露的完整链路。但收益是**运行时灵活性的数量级提升**：同一套注册机制支撑了 CLI、20+ 消息平台、MCP 服务器、cron 调度和 webhook 等完全不同的暴露场景，而无需修改任何工具注册代码。

## 五、总结

```
                    Hermes 工具系统架构总览

  +-------------------------------------------------------------+
  |                      tools/*.py                              |
  |  每个 .py 文件在模块顶层调用 registry.register()            |
  |  AST 扫描 -> 只导入包含注册调用的模块                        |
  +---------------------------+---------------------------------+
                              |
                              v
  +-------------------------------------------------------------+
  |                    ToolRegistry (单例)                       |
  |  ToolEntry (__slots__) | check_fn TTL (30s) | _generation   |
  |  影子覆盖保护 (3级策略) | dynamic_schema_overrides           |
  |  _snapshot_state() -> 线程安全快照                          |
  +---------------------------+---------------------------------+
                              |
                              v
  +-------------------------------------------------------------+
  |                    toolsets.py                               |
  |  _HERMES_CORE_TOOLS (~50) + 平台扩展                        |
  |  递归组合 (includes) + 菱形依赖 (visited)                   |
  |  hermes-* 自动生成 (platform_registry)                      |
  +---------------------------+---------------------------------+
                              |
                              v
  +-------------------------------------------------------------+
  |               agent/tool_guardrails.py                      |
  |  IDEMPOTENT vs MUTATING 分类                                |
  |  ToolCallSignature (SHA-256)                                |
  |  allow / warn / block / halt 四级决策                       |
  |  渐进式阈值 (warn 默认开启, hard_stop 需 opt-in)            |
  +-------------------------------------------------------------+
```

三个子系统各司其职：**注册中心**回答"有哪些工具"，**工具集**回答"用哪些工具"，**护栏**回答"能不能这么用"。这种分层使得 Hermes 能够在不修改任何工具代码的前提下，灵活适配从个人 CLI 到企业级多平台网关的完整场景谱系。
