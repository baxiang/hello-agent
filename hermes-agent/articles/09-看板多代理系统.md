# Hermes Agent 看板多代理系统：SQLite 驱动的协作任务引擎

> **项目**: [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) v0.15.1
> **核心文件**: `hermes_cli/kanban.py` · `hermes_cli/kanban_db.py` · `tools/kanban_tools.py` · `hermes_cli/kanban_swarm.py`
> **关键词**: Kanban Board · Multi-Agent Collaboration · Dispatcher · Circuit Breaker · Board/Tenant Isolation

---

## 引言：为什么 Agent 需要看板

单个 Agent 处理单个任务是直观的。但当你有 5 个 Profile——分别擅长前端、后端、DevOps、代码审查和文档——需要协作完成一个复杂项目时，"谁做什么、以什么顺序、阻塞了怎么办"立刻变成了分布式系统问题。

Hermes 的看板多代理系统正是为此设计的：它不是简单的 TODO 列表，而是一个**带原子认领、依赖解析、断路器、心跳存活检测和自动调度**的持久化协作引擎。全部用 SQLite 实现，零外部依赖。

## 一、数据模型：Board 与 Tenant 的双层隔离

### 1.1 Board：硬边界

Board 是 Hermes 看板的最高级隔离单元。每个 Board 拥有独立的 SQLite 数据库文件，独立的 workspace 目录，独立的 dispatcher 循环。切换 Board 意味着切换到完全不同的任务队列：

```
~/.hermes/kanban/boards/
├── default/kanban.db
├── atm10-server/kanban.db
├── blog-redesign/kanban.db
└── _archived/old-project/kanban.db
```

关键设计：Board 通过 `HERMES_KANBAN_BOARD` 环境变量解析，CLI 的 `--board <slug>` 标志只是设置此变量的一种方式。Dispatcher 和 Worker 进程通过相同的环境变量机制连接到正确的 Board——**一致性是特性，不是 bug**。

```python
# CLI 中对 --board 的处理：临时覆盖 HERMES_KANBAN_BOARD
os.environ["HERMES_KANBAN_BOARD"] = normed
# ... 执行子命令 ...
# finally 块中恢复原值
```

Board 管理命令 (`hermes kanban boards`) 不受 `--board` 参数影响——它们操作的是 Board 元数据和 `current` 指针本身，而非任务数据。

### 1.2 Tenant：软命名空间

Tenant 是 Board 内的逻辑分组，不产生新的数据库。同一个 Board 上的任务可以用 `--tenant backend` 和 `--tenant frontend` 标记，实现软隔离：

```python
p_create.add_argument("--tenant", default=None, help="Tenant namespace")
```

Dispatcher 不强制 Tenant 隔离——同一 Board 内的不同 Tenant 任务可以并行运行。Tenant 主要用于：
- `kanban list --tenant backend` 过滤视图
- `kanban watch --tenant backend` 事件流过滤
- Dispatcher 的 Tenant 感知调度（按 Tenant 限制并发数）

### 1.3 任务状态机

```
         +---------+
         |  todo   |  等待人工排期 / 依赖未就绪
         +----+----+
              |
              v  (依赖全部完成 → promote)
         +---------+
         |  ready  |  等待 Dispatcher 认领
         +----+----+
              |
              v  (atomic claim by Dispatcher)
         +---------+
         | running |  Worker 进程正在执行
         +----+----+
              |
    +----+----+--------+--------+
    |    |    |        |        |
    v    v    v        v        v
  done  blocked  crashed  timed_out  gave_up
```

`blocked` 状态有两个来源：Dispatcher 自动阻塞（断路器触发）和人工阻塞（`kanban block`）。`scheduled` 是 v2 新增的状态，用于表示任务因时间约束而暂缓。

## 三、Dispatcher：调度循环的心脏

### 3.1 循环流程

Dispatcher 是一个长生命周期循环（默认每 60 秒 tick 一次），执行以下步骤：

```
1. reclaim_stale_claims()
   扫描所有 running 状态的任务
   → 检查 claim TTL（默认 900 秒）
   → 过期的：释放认领，回退到 ready 或 blocked
   → 同时清理已不存在的进程

2. promote_ready_tasks()
   扫描所有 todo 状态的任务
   → 检查父依赖是否全部 done/archived
   → 满足条件的提升到 ready

3. claim_and_spawn()
   扫描所有 ready 状态的任务（按 priority DESC）
   → 原子认领（UPDATE ... WHERE status='ready' LIMIT 1）
   → 为每个任务 spawn 独立的 hermes 子进程
   → 传入 --profile <assignee> 标志
```

### 3.2 原子认领机制

认领操作的关键是一行 SQL：

```sql
UPDATE tasks
SET status = 'running',
    assignee = ?,
    started_at = ?,
    session_id = ?
WHERE id = ? AND status = 'ready';
```

`WHERE status = 'ready'` 是原子性的关键——SQLite 的单写者模型保证了同一时间只有一个 Dispatcher tick 能认领到同一任务。不需要分布式锁，不需要 Redis，不需要协调服务。

### 3.3 工作空间创建

每个被认领的任务会获得一个独立的工作空间：

- **scratch**：临时目录（`/tmp/hermes-kanban-<task_id>-<random>/`），任务完成后自动清理
- **worktree**：基于指定路径或默认路径创建 git worktree，分支名如 `wt/t<task_id>-<slug>`
- **dir**：使用已有目录作为工作空间
- **worktree:`<path>`**：在指定 repo 中创建 worktree

### 3.4 Gateway 内嵌调度 vs 独立守护进程

v0.15+ 版本中，Dispatcher 默认运行在 Gateway 进程内部：

```yaml
# config.yaml
kanban:
  dispatch_in_gateway: true   # 默认开启
  dispatch_interval_seconds: 60
```

`kanban daemon` 命令已被标记为 DEPRECATED。Gateway 模式的优势：

- 单进程管理，无需额外守护进程
- Gateway 状态与 Dispatcher 状态一致
- 减少了"双重调度"的 bug（Gateway 和独立 Daemon 同时认领同一任务）

CLI 的 `_check_dispatcher_presence()` 函数在创建任务时检查 Gateway 是否在运行，并给出人类可读的指导。

## 五、断路器：自动故障隔离

### 5.1 故障计数

每次 Worker 进程以非成功状态结束（`spawn_failed`, `timed_out`, `crashed`），Dispatcher 记录一次失败。连续失败次数存储在任务的 `consecutive_failures` 字段中。

### 5.2 断路器触发

```python
# 默认配置
kanban.failure_limit: 2  # 连续 2 次非成功尝试后自动 block

# 每个任务可以覆盖（kanban create --max-retries 3）
```

当 `consecutive_failures >= failure_limit` 时，Dispatcher 自动将任务状态切换到 `blocked`，并在任务事件中记录 `auto_blocked` 事件。

断路器不会永久禁止重试——用户可以手动 `kanban unblock` 将任务移回 ready。这保证了系统在遇到难以处理的故障时**优雅降级而非无限重试**。

### 5.3 手动阻塞与自动阻塞的区别

```
手动阻塞 (kanban block #42 "waiting for API access"):
  → 立即生效，附带人类可读原因
  → reason 作为评论追加

自动阻塞 (断路器触发):
  → 仅在 Dispatcher tick 时触发
  → reason 包含最近 N 次失败的诊断摘要
  → 附带 gave_up 或 crashed 事件
```

## 六、心跳与存活检测

### 6.1 心跳机制

长时间运行的 Worker 可以调用 `kanban_heartbeat` 工具，写入一条 `heartbeat` 事件：

```python
def _cmd_heartbeat(args):
    with kb.connect_closing() as conn:
        ok = kb.heartbeat_worker(conn, task_id, note="rendering frame 847/3000")
```

### 6.2 Stale Claim 检测

Dispatcher 的 `reclaim_stale_claims()` 步骤检查：

1. Claim 是否超过 TTL（默认 900 秒）
2. Worker 进程是否仍然存活（通过 PID 检查）
3. 最后一次心跳是否在规定窗口内

满足任何一个条件就会 reclaim 任务。Reclaim 不会删除已完成的工作——Worker 日志和部分输出会保留，下次运行可以继续。

## 七、Kanban Swarm：并行图形编排

`kanban swarm` 是 v1 中引入的并行编排模式：

```
              +----------------+
              |  Root (anchor)  |
              +-------+--------+
                      |
          +-----------+-----------+
          |           |           |
    +-----v----+ +---v----+ +---v------+
    | Worker A | |Worker B| | Worker C  |  并行执行
    +-----+----+ +---+---+ +-----+----+
          |          |           |
          +-----+----+----+------+
                      |
               +------v------+
               |  Verifier   |  验证结果
               +------+------+
                      |
               +------v------+
               | Synthesizer |  合成最终输出
               +-------------+
```

命令行创建方式：

```bash
hermes kanban swarm "Build a multi-tenant SaaS boilerplate" \
  --worker frontend-dev:frontend \
  --worker backend-dev:backend:"database-api,auth" \
  --worker devops:infrastructure \
  --verifier code-reviewer \
  --synthesizer tech-writer
```

Swarm 内部创建链路依赖关系：Root → Workers → Verifier → Synthesizer。Dispatcher 自动解析依赖关系，依次调度。

## 十、设计哲学：为什么用 SQLite？

在一个微服务和分布式数据库横行的时代，用 SQLite 做多代理协作引擎看似"简陋"，但这是深思熟虑的选择：

1. **零运维**：无需配置数据库服务器，无需网络连接，无需认证。`kanban init` 后就立即可用
2. **原子认领**：SQLite 的单写者模型天然提供 `UPDATE WHERE status='ready'` 的原子性，不需要分布式锁
3. **可调试**：`sqlite3 kanban.db "SELECT * FROM tasks"` 就是全部诊断工具
4. **可备份**：复制一个 100KB 的文件就是完整备份
5. **Board 隔离**：一个 Board 一个文件，天然隔离，`hermes kanban boards create` 就是创建一个新文件

对于 99% 的看板使用场景，SQLite 的性能完全够用。Hermes 的设计者清楚地知道"够用就够了"。

## 总结

Hermes 看板系统是一个**完整的、自包含的多代理协作引擎**：

```
+------------------+     +------------------+     +------------------+
|   kanban CLI      |     |   Dispatcher      |     |   Worker Process  |
|  (create/list/...) |    |  (reclaim/promote/ |    |  (hermes -p name)  |
|                    |     |   claim/spawn)     |    |                    |
+--------+----------+     +---------+---------+     +----------+--------+
         |                          |                          |
         +--------------------------+--------------------------+
                                    |
                           +--------v--------+
                           |   SQLite DB      |
                           |  (kanban.db)     |
                           +--------+--------+
                                    |
                    +---------------+----------------+
                    |               |                |
             Board isolation   Tenant namespace   Event timeline
```

它的核心价值不在于"又一个 TODO 列表"，而在于让多个独立配置、独立身份、独立能力的 Agent Profile 像人类团队一样协作——谁在做什么、做完了没有、阻塞了为什么、失败了怎么办——这一切都由 SQLite 中的几张表和几百行调度逻辑来保证。
